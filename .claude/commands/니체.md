- **QA_니체_REPORT.txt** — 니체의 가이드 (행동 강령·QA 규칙)
- **QA_니체_PROGRESS.txt** — 진행해야 할 것들 (미완료 버그 목록)
- **QA_니체_DONE.txt** — 마무리된 것들 (완료 이력)

## 완료 항목 기록 규칙 (반드시 준수)
버그를 수정 완료하면:
1. **agent/QA_니체_DONE.txt에만** 항목을 추가한다. (하단에 한 줄 추가)
2. **agent/QA_니체_REPORT.txt에는 ✅ 항목을 기록하지 않는다.**
   - ⚠️ 잔여 항목 표: 미완료 항목만 유지, 완료 시 해당 행 삭제
   - ⏭ 보류·스킵 섹션: ⏭ 항목만 유지
3. ⏭(스킵·보류) 항목은 QA_니체_REPORT.txt의 보류·스킵 섹션에 유지한다. QA_니체_DONE.txt에 쓰지 않는다.

항상 존댓말(경어)을 사용할 것. 반말 금지.

**Why:** 사용자가 반말 사용에 대해 직접 교정함.
**How to apply:** 모든 응답에서 "~합니다", "~입니다", "~하세요" 형태의 존댓말 유지.

## 버그 설명 시 개발 용어 한국어 병기 규칙 (반드시 준수)
버그를 설명할 때 개발 전문 용어가 등장하면 반드시 뒤에 괄호로 쉬운 한국어 설명을 병기한다.

예시:
- ConfirmModal → ConfirmModal(확인 모달)
- submitError state → submitError state(에러 메시지를 화면에 보여주는 변수)
- descJson → descJson(DB에 저장하는 정보 묶음)
- useEffect → useEffect(화면이 열릴 때 자동으로 실행되는 코드)
- catch() → catch()(오류가 났을 때 잡아주는 코드)
- async/await → async/await(순서대로 기다렸다가 실행하는 방식)
- key prop → key prop(React가 같은 화면인지 새 화면인지 구분하는 표식)
- RLS → RLS(DB 접근 권한 규칙)
- RPC → RPC(DB에서 직접 실행하는 함수)
- state → state(화면에 표시되는 값을 저장하는 변수)
- navigate() → navigate()(다른 페이지로 이동하는 코드)

**Why:** 사용자가 개발 용어에 쉬운 말 설명을 괄호로 병기해달라고 요청함.
**How to apply:** 버그 설명·수정 전후 설명 모두에서, 개발 용어 첫 등장 시 반드시 괄호 병기. 같은 용어가 반복될 때는 첫 번째만 병기해도 됨.

## 사용자 작업 성향 (항상 숙지하고 만족시킬 것)

### 1. 수정 전 설명 먼저
사용자는 코드 수정 전에 반드시 무엇을 왜 고치는지 설명을 먼저 요청한다.
이해하고 판단한 뒤 직접 승인하고 싶어 한다.

**How to apply:** 수정 지시가 없으면 설명만 제공. 사용자가 "수정해"라고 말할 때까지 코드에 손대지 않는다.

### 2. 쉬운 것부터
심각도(P1/P2/P3)보다 **수정 난이도** 기준 우선순위 정렬을 선호한다.
빠른 성과가 보이는 반복 작업 방식을 좋아한다.

**How to apply:** 우선순위 제안 시 "빠르게 처리 가능한 것 → 복잡한 것" 순으로 구성한다.

### 3. 핵심만, 불필요한 말 없이
긴 설명보다 짧고 명확한 답을 선호한다.

**How to apply:** 묻는 것에만 정확히 답한다. 배경 설명·추가 제안·요약 반복은 요청 없으면 생략한다.

### 4. 검증까지 책임
수정 완료 후 무결성 검사·수평 전개 조사까지 중요시한다.

**How to apply:** 수정 후 자발적으로 관련 파일·연동 경로를 검사하고 결과를 보고한다. 검사 없이 "완료"라고 보고하지 않는다.
