D-48. staggered 애니메이션을 setTimeout 체인으로 구현하면 누적 드리프트로 일괄 동기화 ✅ 해결
     → 증상: 20개 태그가 개별 setTimeout으로 각자 사이클을 돌리면 처음엔 엇갈리다가
             시간이 지나면서 오차가 누적되어 결국 여러 개가 동시에 나타났다 사라지는 배치 현상 발생
     → 원인: setTimeout은 정밀도 보장이 없음 (브라우저 throttle, 탭 비활성 등으로 수십~수백ms 지연 가능)
             각 태그가 독립 setTimeout 체인으로 동작하면 사이클마다 오차가 누적되어 결국 동기화됨
     → 해결: requestAnimationFrame 단일 루프 + 수식 기반 phase 계산으로 교체
             phase = ((elapsed - i*STAGGER - pausedMs) % T_CYCLE + T_CYCLE) % T_CYCLE
             - elapsed: 공유 시작시각 기준 경과 시간 (드리프트 없음)
             - i*STAGGER: 태그별 고정 오프셋 (비율로 균등 분배)
             - pausedMs: 호버 일시정지 누적 시간 (hoverStartRef + totalPauseRef 패턴)
             → 모든 태그가 동일 클락을 공유하므로 영구적으로 균등 간격 보장
     → 원칙: 여러 요소가 균등한 시간차로 반복 애니메이션해야 할 때 setTimeout 체인은 절대 사용 금지
             단일 rAF + 수식 계산 패턴만이 드리프트 없이 항상 정확한 동시 노출 수를 보장함
             React state 대신 DOM 직접 조작(el.style.opacity)으로 리렌더 없이 60fps 유지

D-63. CSS 키프레임 애니메이션을 루프에서 재시작하려면 React key 교체로 강제 리마운트 필요 ✅ 해결
     → 증상: 루핑 phase 머신에서 phase가 0으로 리셋될 때 SVG stroke-dashoffset 애니메이션이 처음부터 재실행되지 않음
     → 원인: 동일 DOM 요소에 animation 속성을 'none'으로 변경 후 다시 설정해도 브라우저가 새 애니메이션으로 인식하지 않는 경우가 있음
             (animationName 변경 없이 animation 프로퍼티만 토글 시 브라우저가 같은 애니메이션으로 간주 → 재시작 미실행)
     → 해결: 애니메이션 대상 요소에 `key={phase < N ? 'reset' : 'active'}` 부여
             key 변경 → React가 요소를 언마운트 후 새로 마운트 → 브라우저가 애니메이션을 항상 첫 프레임부터 실행
             예) `<polygon key={phase < 2 ? 'r' : 'a'} style={{ animation: phase >= 2 ? 's3_drawR 1.1s ease forwards' : 'none' }} />`
     → 원칙: CSS keyframe 애니메이션을 React 루프/페이즈 머신에서 반복 재시작해야 할 때
             animation 속성 토글만으로는 신뢰할 수 없음 — React key 교체로 강제 리마운트가 유일하게 확실한 방법
             key 교체 대상은 애니메이션 요소 자체여야 하며, 상위 컨테이너에 붙이면 의도치 않게 전체 레이아웃을 재계산함


D-81. Windows Node.js에서 import.meta.url의 드라이브 레터가 소문자로 반환되어 regex 미매칭으로 이중 경로 생성 패턴 ✅ 해결
     → 증상: `node scripts/create-12-test-missions.mjs` 실행 시 `ENOENT: no such file or directory, open 'c:\c:\Users\...'` 오류
     → 원인: Node.js가 Windows에서 `import.meta.url`의 드라이브 레터를 소문자(`c:`)로 반환하는데,
             기존 정규식 `/^\/([A-Z]:)/`가 대문자만 매칭 → replace 미실행 → `/c:/...` 경로가 그대로 남아
             `.pathname`이 `/c:/Users/...` 형태 → 앞 슬래시 제거 실패 → `c:\c:\Users\...` 이중 경로 생성
     → 해결: 정규식에 소문자 드라이브 레터도 포함:
             `replace(/^\/([A-Za-z]:)/, '$1')` (기존 `[A-Z]` → `[A-Za-z]`)
     → 적용 파일: `scripts/*.mjs` 파일 상단 .env.local 경로 파싱 코드 전체
     → 원칙: Windows에서 `new URL('../.env.local', import.meta.url).pathname`으로 경로를 얻을 때
             드라이브 레터 대소문자를 가정하지 말 것 — `[A-Za-z]`로 대소문자 모두 포함해야 함
             macOS/Linux에서는 드라이브 레터가 없으므로 이 정규식이 아무 효과 없이 안전하게 통과됨


D-84. 한글 IME 활성 중 SQL 파일 편집 시 자모 문자 혼입으로 PostgreSQL parse 오류 패턴 ✅ 해결
     → 증상: supabase db push 실행 시 특정 migration이 "syntax error" 로 실패
             실패한 migration 이후 모든 migration도 연쇄 미적용
             이전 버전(버그 있는) 함수가 DB에 잔류해 기능 오류 지속
     → 원인: 한글 IME(입력기)가 활성화된 상태에서 SQL 파일의 특정 키워드를 입력할 때
             IME가 영문자를 한글 자모(ㅔ, ㅁ, ㅇ 등)로 오해해 Unicode 자모 코드포인트를 삽입함
             예) `SECURITY DEFINER` 뒤 + IME 활성 상태 → `SECURITY DEFINERㅔ`
                 `AS $$` 앞 + IME 활성 → `AS $ㅔ$`
             자모 문자(U+3131~U+314E, U+3154 등)는 일반 텍스트 에디터에서 눈에 잘 안 띄며,
             PostgreSQL은 해당 위치를 "syntax error at or near 'ㅔ'"로 보고하지 않고
             전혀 다른 위치의 오류처럼 보고할 수 있어 원인 파악이 매우 어려움
     → 해결 1 (즉각): 해당 줄을 재입력하거나 자모 문자만 정확히 삭제
                       VS Code의 경우 Ctrl+G(줄 이동) 후 해당 문자 위치에서 Backspace/Delete
     → 해결 2 (안전망): 동일 함수를 재정의하는 후속 migration을 추가해 DB 적용 상태 보장
                        (migration 049가 migration 046 parse 오류의 안전망으로 047 함수를 재적용한 패턴)
     → 탐지 방법: `grep -P '[\x{3131}-\x{314E}\x{3154}-\x{3163}]' *.sql` 로 자모 문자 전수 검색
                  VS Code: Ctrl+F → 정규식 모드 → `[ㄱ-ㅎㅔ-ㅣ]` 패턴으로 검색
     → 원칙: SQL 파일(특히 SECURITY DEFINER, LANGUAGE, AS $$...$$, RETURNS 등 키워드 근처)을
             한국어 환경에서 편집할 때는 IME가 꺼진 상태인지(영문 입력 모드) 반드시 확인할 것
             git diff로 해당 줄에 비ASCII 문자가 포함되어 있으면 migration push 전 반드시 제거
             migration 실패 후 연쇄 미적용이 의심될 때는 실패 migration 파일의 자모 문자 여부부터 확인할 것


D-95. 파일 업로드가 포함된 가입 흐름에서 signOut 전에 업로드해야 하는 타이밍 패턴 ✅ 정착
     → 문제: signUp() 성공 후 signOut() 호출 → signOut() 이후에 Storage 업로드 시도 시
             인증 세션이 없어 "Unauthorized" 또는 RLS 차단 오류 발생
             파일 업로드와 panels UPDATE 모두 세션이 필요한 인증된 요청임
     → 원인: 이메일 가입 흐름: signUp() → 세션 활성 → signOut() → 로그인 페이지 이동
             세션 활성 구간이 signUp()과 signOut() 사이에만 존재
             File 객체는 sessionStorage.setItem()으로 직렬화 불가 (TypeError: cyclic object value)
             → sessionStorage에 File 저장 시도 자체가 실패하거나 null로 저장됨
     → 해결: signUp() 반환값에서 user.id 캡처 → 세션 활성 상태에서 즉시 Storage 업로드 → panels UPDATE → signOut()
             ```js
             const signUpData = await signUp({ email, password, name, role });
             const panelUserId = signUpData?.user?.id;
             if (role === 'panel' && panelUserId) {
               // 파일 업로드 및 panels UPDATE (세션 활성 상태)
               await supabase.storage.from('panel-verification-docs').upload(path, file, { upsert: true });
               await supabase.from('panels').update(payload).eq('user_id', panelUserId);
             }
             await signOut();  // 업로드 완료 후에 signOut
             ```
     → 원칙: signUp()과 signOut() 사이의 세션 활성 구간을 파악하고,
             가입 직후 즉시 처리해야 하는 인증 필요 작업(파일 업로드, 프로필 초기화 등)을
             반드시 signOut() 호출 전에 완료할 것
             File 객체는 항상 세션 내에서 직접 업로드해야 하며, 세션 밖으로 전달 불가
             uploadErr가 발생해도 가입 흐름은 계속 진행(console.warn 후 path=null) — graceful fallback
     → 추가: private Storage 버킷에서는 getPublicUrl 무효 — path만 DB에 저장하고
             어드민 접근 시 createSignedUrl(path, 600)으로 10분 유효 signed URL 생성
