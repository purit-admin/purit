     → 현재 Supabase 연동 완료: companies, panels, missions, feedbacks 테이블

C-2. 트리거 의존 로직 주의
     → 회원가입 시 DB 트리거(handle_new_user)가 자동으로 panels 또는 companies 레코드 생성
     → 프론트엔드 코드에서 signUp 후 수동으로 테이블 INSERT 하지 말 것 (중복 생성 위험)

C-3. 인증 상태는 useAuth() 훅 사용
     → supabase.auth.* 를 직접 호출하지 말고, useAuth 훅의 메서드 사용
     → 예외: AuthContext.jsx 내부 구현

C-4. 피드백 제출 시 3개 테이블 동시 업데이트 패턴 유지
     → feedbacks INSERT → missions.filled_count UPDATE → panels.total_missions UPDATE
     → 순서 변경 금지, 오류 발생 시 전체 롤백 고려
     ※ filled_count / total_missions 증가는 반드시 RPC 사용 (직접 UPDATE 금지)
        - increment_mission_filled_count(mission_id UUID)
        - increment_panel_mission_count(panel_id UUID)
        이유: RLS가 패널의 missions/panels 직접 UPDATE를 에러 없이 무시(0행 업데이트)함

C-5. RLS silent failure 패턴 주의
     → Supabase RLS가 UPDATE를 막을 때 에러를 반환하지 않고 0행 업데이트로 조용히 실패함
     → supabase.from().update() 성공 여부는 error가 아니라 실제 DB 반영 여부로 확인해야 함
     → 크로스 테이블 UPDATE(패널이 missions 업데이트, 기업이 panels 업데이트 등)는
        SECURITY DEFINER RPC 함수를 통해서만 처리할 것
     → 현재 등록된 RLS 정책: panels(SELECT/UPDATE), companies(SELECT/UPDATE),
        missions(SELECT/INSERT/UPDATE), feedbacks(SELECT/INSERT/UPDATE)

D-50. useEffect cleanup을 async 함수 내부에서 return하면 cleanup이 절대 실행되지 않음 ✅ 해결
     → 증상: Supabase Realtime 구독이 컴포넌트 언마운트 후에도 살아있어 메모리 누수 + 경고 발생
     → 원인: async 함수는 항상 Promise를 반환하므로, async 함수 안에서 `return () => cleanup()`을 써도
             useEffect는 cleanup 함수를 받지 못함 (Promise를 받음 — 무효)
             ```js
             useEffect(() => {
               async function load() {
                 // ...
                 const sub = supabase.channel(...).subscribe();
                 return () => supabase.removeChannel(sub); // ← 이 return은 load()의 return (Promise 내부)
               }
               load(); // load()의 반환값(Promise)을 무시 → useEffect cleanup 없음
             }, []);
             ```
     → 해결: let sub = null 을 async 함수 밖(useEffect 콜백 최상단)에 선언,
             async 함수 내부에서 sub에 할당만 하고,
             cleanup return은 useEffect 콜백 최상단에서 직접 반환
             ```js
             useEffect(() => {
               let sub = null;
               async function load() {
                 // ...
                 sub = supabase.channel(...).subscribe();
               }
               load();
               return () => { if (sub) supabase.removeChannel(sub); }; // ← useEffect가 이걸 cleanup으로 받음
             }, []);
             ```
     → 원칙: useEffect 내에서 async 함수를 호출할 때, cleanup(구독 해제·타이머 취소 등)은
             반드시 async 함수 밖 useEffect 콜백 최상단에서 return해야 한다
             async 함수 안의 return은 useEffect cleanup으로 전달되지 않는다

D-69. ConfirmModal onConfirm에 async 함수를 await 없이 호출하면 DB 완료 전 모달이 닫혀 에러 영구 비노출 ✅ 해결

     → 원인: `onConfirm={() => { handleRemove(id); setConfirmX(null); }}`

     → 원칙: JSX 이벤트 핸들러에서 async 함수를 호출할 때는 반드시 async 콜백 + await 조합을 사용할 것

             에러가 발생 가능한 액션이 있는 모든 뷰에 해당 에러 렌더 블록이 있는지 확인할 것

D-75. async 함수가 내부에서 try-catch-console.error만 하고 re-throw 하지 않으면 호출자가 항상 성공으로 인식해 데이터 소실을 유발하는 패턴
     → 증상: "임시 저장 후 나가기" 버튼 클릭 시 DB 실패가 발생해도 모달이 닫히고 다음 페이지로 이동.
             사용자는 저장이 된 것으로 착각하지만 데이터는 소실됨 (콘솔에만 에러 출력)
     → 원인: saveDraft() 내부에서 catch(e) { console.error(...) } 로 에러를 삼킴
             → async 함수가 에러를 throw하지 않으면 반환 Promise는 항상 resolved 상태
             → 호출자에서 `await saveDraft()` 는 DB 실패 여부와 관계없이 항상 정상 완료로 인식
             → `await saveDraft(); navigate(dest);` 패턴에서 navigate는 항상 실행됨
     → 해결: 저장 실패를 호출자에게 전파해야 하는 async 함수의 catch에서 반드시 re-throw:
             ```js
             } catch (e) {
               console.error('[SaveDraft] 실패:', e.message);
               setSavingDraft(false);
               throw e;  // ← 호출자에게 에러 전파 필수
             }
             setSavingDraft(false);  // ← finally 대신 try 마지막에 배치 (re-throw 후 finally는 실행되나 throw가 이미 진행됨)
             ```
             호출자에서 try-catch로 잡아 실패 시 이동 차단 + 에러 메시지 표시:
             ```js
             try { await saveDraft(); } catch { setError('저장 실패'); return; }
             navigate(dest);  // ← 성공 시에만 실행
             ```
     → 원칙: "에러를 잡되 UI에는 표시하지 않는다"는 내부 catch 패턴은 일반 fire-and-forget에서만 허용.
             호출자가 성공/실패를 구분해야 하는 중요 작업(데이터 저장, 결제, 상태 변경)은
             반드시 에러를 re-throw해 호출 체인 전체가 실패를 인지할 수 있게 해야 함
             catch 안에 re-throw 없음 = "에러를 삼킴" = 호출자 입장에서 항상 성공

D-78. justifyContent는 CSS transition 불가 속성 — 값이 바뀌면 즉각 점프, paddingLeft로 대체 ✅ 해결
     → 증상: 사이드바 열림/닫힘 시 아이콘이 smooth하게 이동하지 않고 center ↔ flex-start 사이에서 즉시 튀어 버벅이는 것처럼 보임
     → 원인: `justifyContent: isExpanded ? 'flex-start' : 'center'` 토글에 CSS transition을 걸어도 효과 없음
             justifyContent, alignItems, display, whiteSpace 등 레이아웃 계산 방식을 바꾸는 속성은 브라우저가 보간(interpolate) 자체를 지원하지 않아 transition 대상이 될 수 없음
             → `transition: '... justify-content 0.3s'` 을 추가해도 transition이 발동되지 않고 값이 즉시 점프
     → 해결: `justifyContent: 'flex-start'` 고정 (절대 변경 안 함)
             아이콘 중앙 정렬 효과는 paddingLeft로 시뮬레이션:
               - 접힘(60px 사이드바, 버튼 48px, 아이콘 16px): paddingLeft = (48-16)/2 = 16px → 아이콘 시각적 중앙
               - 펼침: paddingLeft = 12px (좌측 정렬 기준점)
             `paddingLeft: isExpanded ? 12 : 16` + `transition: 'padding-left 0.3s cubic-bezier(0.4,0,0.2,1)'`
             → paddingLeft는 CSS-animatable — 아이콘이 0.3s 동안 부드럽게 슬라이드
     → CSS transition 불가 속성 목록 (대표): justifyContent, alignItems, display, flexDirection, whiteSpace, position
     → CSS transition 가능 속성 목록 (레이아웃 관련): width, height, maxWidth, maxHeight, padding-left/right/top/bottom, margin, gap(Chrome 99+), opacity, border-radius
     → 원칙: flexbox 정렬 방식을 전환하며 smooth 애니메이션이 필요할 때는
             justifyContent/alignItems 토글 대신 padding/margin 보간으로 시각적 동등 효과를 구현할 것
             "transition을 걸었는데 여전히 튀는" 현상 = 해당 CSS 속성이 animatable하지 않다는 신호

     → 증상: expire_all_panel_drafts(pg_cron)와 expire_panel_drafts(패널 접속 시)가 동시에 실행될 때

             두 트랜잭션이 동일 행을 SELECT한 뒤 각자 UPDATE를 실행할 수 있음

             ```sql
             UPDATE feedbacks SET status = 'rejected' WHERE id = rec.id AND status = 'draft';
             GET DIAGNOSTICS v_deleted_row = ROW_COUNT;
             IF v_deleted_row > 0 THEN
               UPDATE missions SET filled_count = GREATEST(0, filled_count - 1) WHERE id = rec.mission_id;
             END IF;
             ```

             cleanup에서 supabase.removeChannel(subscription)을 올바르게 호출하는 것만으로는 StrictMode 이중 실행을 방어하기에 불충분

D-97. signUp() 후 signOut() 완료 전 navigate() 호출 시 목적지 페이지에서 stale user 세션으로 auto-redirect가 발동하는 Race Condition 패턴 ✅ 해결
     → 증상: 이메일 회원가입 완료 후 로그인 페이지로 이동했을 때 "로그인 처리 중..." 버튼이 순간 깜빡이거나,
             대시보드로 이동했다가 다시 로그인 페이지로 튕겨 돌아오는 현상 발생
     → 원인: Supabase는 signUp() 성공 시 자동으로 세션을 생성함 (사용자가 즉시 로그인됨)
             Signup.jsx 흐름: signUp() → SIGNED_IN 이벤트 비동기 발화 시작 → signOut() → SIGNED_OUT 이벤트 비동기 발화 시작 → navigate('/login')
             navigate('/login')이 실행되는 시점에 onAuthStateChange SIGNED_OUT 이벤트가 아직 처리 중일 수 있어
             AuthContext의 user 값이 여전히 non-null인 채로 Login 컴포넌트가 마운트됨
             Login.jsx useEffect: `if (user && authRole) navigate(DEST[authRole])` → 대시보드로 redirect
             그 직후 SIGNED_OUT 완료 → user = null → 대시보드 RoleRoute가 /login으로 다시 튕김
             이 ping-pong 과정에서 로딩 상태가 순간 노출됨
     → 핵심 오해: await signOut()이 완료되었다고 React state(user)가 동기적으로 null이 되지 않음
             onAuthStateChange는 비동기 이벤트 — setState는 다음 render cycle에서야 적용됨
             navigate() 직후 컴포넌트가 마운트되는 시점의 user 값은 이전 render의 stale 값일 수 있음
     → 해결: Login.jsx auto-redirect useEffect에 successMsg 가드 추가
             ```jsx
             useEffect(() => {
               if (successMsg) return; // 가입 완료 직후는 자동 redirect 안 함
               if (user && authRole) navigate(DEST[authRole] ?? '/company', { replace: true });
             }, [user, authRole]);
             ```
             successMsg는 이메일 가입(location.state?.message)·Google OAuth 가입(?signup=google) 모두 truthy
             → 두 가입 경로 모두 커버 / 일반 로그인(successMsg='') 시 auto-redirect 정상 동작 유지
     → 원칙: "로그인 중인 사용자를 대시보드로 보내는 useEffect"가 있는 페이지로 navigate 직전에
             signOut()을 호출하는 패턴은 항상 이 Race Condition에 취약함
             해결 방향: navigate() 대상 페이지에서 "가입 완료 상태"를 감지해 auto-redirect를 선택적으로 억제할 것
             location.state.message 또는 URL 파라미터(signup=google)를 "auto-redirect 억제 신호"로 활용하는 것이 최소 침습적 해결책

D-98. SECURITY DEFINER RPC의 DECLARE 변수 타입이 실제 DB 컬럼 타입과 불일치하면 SELECT INTO 시 암묵적 캐스팅 실패로 RPC 전체가 NULL 반환하는 패턴 ✅ 해결
     → 증상: `/share/:token` 공유 페이지 전체가 404("공유 링크를 찾을 수 없습니다") 화면 표시
             `supabase.rpc('get_shared_mission', { p_token })` 반환값이 error=null인데도 data=null
             특정 토큰만 실패하는 것이 아니라 모든 share 링크가 동일하게 404
     → 원인: DECLARE 섹션의 변수 타입이 SELECT INTO 대상 컬럼의 실제 타입과 다를 때
             PostgreSQL이 암묵적 캐스팅을 시도하다 실패하면 EXCEPTION을 발생시키지 않고
             SELECT INTO 결과 전체를 NULL로 처리하는 경우가 있음
             구체적 사례: `v_persona JSONB;` 로 선언 후 `missions.persona` (TEXT 컬럼) 값을 SELECT INTO 시도
             → TEXT→JSONB 암묵적 캐스트 실패 (persona 값이 유효한 JSON 형식이 아닌 자유 텍스트이므로)
             → v_id(UUID)를 포함한 SELECT 전체가 NULL로 취급됨 → `IF v_id IS NULL THEN RETURN NULL;` 조건 충족
             → RPC가 NULL 반환 → 클라이언트 `if (!result)` 조건 → setNotFound(true) → 404 화면
     → 진단 어려움:
             1) 클라이언트에서 error 객체가 null이고 data만 null → 일반적인 "토큰 없음" 케이스와 구별 불가
             2) SQL 로그나 Supabase Dashboard의 Functions 탭에도 에러 로그가 남지 않음
             3) SQL Editor에서 `SELECT get_shared_mission('토큰값');` 을 직접 실행해도 NULL 반환만 확인 가능
             → SQL EXCEPTION이 발생하지 않아 PostgreSQL 에러 로그에도 기록 안 됨
     → 해결: DECLARE 섹션의 모든 변수 타입을 DB 컬럼 실제 타입과 정확히 일치시킬 것
             `v_persona JSONB;` → `v_persona TEXT;` (missions.persona는 TEXT 컬럼)
             점검 방법: 정보 스키마 조회로 대상 컬럼의 실제 타입 확인
             `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'missions';`
     → 원칙: SECURITY DEFINER RPC를 작성할 때 DECLARE 섹션 변수 타입은 반드시 DB 스키마의 실제 컬럼 타입을 조회해 맞출 것
             특히 TEXT와 JSONB/UUID/NUMERIC/TIMESTAMPTZ는 서로 암묵적 캐스트가 보장되지 않음
             "타입이 맞겠지"라는 가정은 절대 금지 — 컬럼 타입 확인 없이 DECLARE를 작성하면
             모든 SELECT INTO가 NULL을 반환하는 무음 실패로 이어질 수 있음
             4_DBSchema.txt의 컬럼 타입 정보를 반드시 참조할 것 (CLAUDE.md 조건부 로드 규칙)

D-100. 대시보드 KPI에서 "미처리 = 전체 - 완료" 공식이 중간 상태(반려 등)를 포함해 실제 미처리 수보다 부풀어 있는 패턴
     → 증상: admin/Dashboard.jsx "검토 대기 피드백: N"이 PurityFilter "검토 대기" 탭 실제 건수보다 항상 크게 표시됨

     → 원인: `pendingFeedbacks = stats.feedbacks - stats.passed`
             stats.feedbacks = submitted(검토중) + rejected(반려됨) + approved(승인됨) — draft 제외 전체
             stats.passed = approved만

     → 해결: 별도 submitted count 쿼리 추가
             `.from('feedbacks').select('*', {count:'exact', head:true}).eq('purity_passed', false).eq('status', 'submitted').neq('status', 'draft')`
             또는 stats.feedbacks - stats.passed - rejectedCount 방식으로 반려 건수를 별도 집계 후 차감
     → 원칙: "미처리 = 전체 - 완료" KPI 공식은 상태가 정확히 2단계(처리중/완료)일 때만 유효함
             처리 흐름이 3단계 이상(검토중 → 승인 or 반려)인 시스템에서는
             반드시 목표 상태(검토중=submitted)를 직접 count하거나
             중간 실패 상태(반려=rejected)를 명시적으로 제외해야 함
             D-68(집계 쿼리 draft 필터 누락)과 유사하지만 원인이 다름:
             D-68은 필터 누락, D-100은 공식 설계 오류 — 두 가지 모두 집계 쿼리 작성 시 점검할 것

D-101. 상태 변경(DB 트리거 발화) + 금전 처리가 별개 작업으로 분리되어 있을 때 트리거가 조기 발화하는 비원자성 패턴

D-103. 이메일 가입(트리거)과 OAuth 가입(RPC) 두 경로가 동일 비즈니스 로직을 처리해야 할 때 한쪽에만 구현하고 다른 쪽을 누락하는 패턴

     → 원칙 1: 테이블에 RLS를 처음 활성화할 때 반드시 다음 3가지 정책을 동시에 추가할 것:

     → 원칙 2: 두 테이블이 서로의 RLS 정책에서 상대방을 조회하면 반드시 순환 참조 발생

     → 원칙 3: GRANT EXECUTE 누락 주의 — SECURITY DEFINER RPC 생성 후 반드시 GRANT 구문 포함할 것

D-116. 동일 localStorage 키를 한 useEffect는 async로 읽고(카운트 계산) 다른 useEffect는 동기로 쓸 때(seen=now) 경쟁 상태로 옛 값 기준 결과가 덮어쓰는 패턴 ✅ 해결
     -> 증상: 어드민 '패널 관리' 메뉴의 신규 심사대기 뱃지가, 정작 패널 관리 페이지를 보고 있는 동안에도 0이 아닌 값으로 잠깐/계속 표시됨.
     -> 원인: 같은 커밋에서 두 useEffect가 함께 실행 — Effect A(loadPending)는 localStorage의 마지막 방문 시각(seenAt)을 읽고
             Supabase count 쿼리를 await로 기다림. Effect B는 동기적으로 seenAt=now()를 쓰고 setCount(0)을 호출.
             Effect A가 B보다 먼저 선언돼 먼저 시작 → 옛 seenAt(또는 null) 기준으로 쿼리가 날아가고,
             B가 0으로 만든 뒤 A의 await가 늦게 resolve되며 setCount(옛값>0)으로 덮어씀.
             "방문 시 0으로 초기화"가 비동기 쿼리 resolve 타이밍 때문에 무효화되는 비직관적 함정.
     -> 해결: async 콜백(loadPending) 진입부에서 window.location.pathname을 직접 확인 —
             현재 그 페이지를 보고 있으면(=이미 '본' 상태) 쿼리 자체를 생략하고 setCount(0) 후 즉시 return.
             pathname을 useEffect deps의 클로저가 아니라 콜백 실행 시점에 직접 읽어 stale 값을 피함.
             (Realtime 구독으로 재호출될 때도 항상 최신 pathname으로 판단됨)
     -> 원칙: "마지막으로 본 시각"을 localStorage에 앵커로 저장해 미확인 수를 세는 패턴에서,
             읽기(async)와 쓰기(sync)가 서로 다른 useEffect에 있으면 반드시 경쟁 상태를 의심할 것.
             async 결과로 state를 setState하기 직전에 "지금도 그 화면을 보고 있는가"를 실시간 값으로 재확인하면
             타이밍에 무관하게 일관된 결과를 보장할 수 있음.

     -> 증상: 패널이 같은 형식 서류를 재제출하면 "건강보험 파일 업로드에 실패했습니다" 400. 최초 제출이나 다른 확장자 제출은 정상 → 간헐 버그처럼 보임.

     -> 원인: 업로드 코드가 고정 경로(`{uid}/health_insurance.{ext}`, `{cid}/{mid}/va.{ext}` 등) + upsert:true.

             해당 버킷에 FOR UPDATE 정책이 있는지 확인할 것. INSERT 정책만 보고 "쓰기 됨"으로 판단하면 재업로드에서 터진다.

D-121. 같은 "동적 가격"을 클라이언트(표시)와 서버(차감) 양쪽에서 계산할 때, 정렬·중복제거·동점처리가 어긋나면 "표시가격 ≠ 결제가격"이 되는 패턴 ✅ 해결
     -> 증상: 무료 체험 언락 비용을 Results.jsx(표시)와 unlock_free_trial_mission RPC(차감)가 각각 계산 → 같은 경력 데이터인데 합계가 달라질 여지. 본 금액과 빠지는 금액 불일치.

     -> 원칙: 표시용·과금용 계산이 분리된 곳은 (a)엔티티 dedup (b)결정론적 정렬 tiebreaker (c)동일 공식 셋을 양쪽에서 동일 보장해야 한다.

D-123. 듀얼(2핸들) 레인지 슬라이더를 native <input type=range>로 만들면 (a)두 input 겹침 시 위 input이 클릭 독점 (b)핸들이 양 끝에서 삐져나옴 — 둘 다 native로는 해결 불가 ✅ 해결

     -> 증상 2(삐져나옴): Chrome은 native 핸들을 값 위치에 정확히 중앙정렬하고 양끝 inset을 안 줌 → 가운데는 OK, 양 끝으로 갈수록 핸들 바깥 절반이 트랙을 넘어 삐져나옴이 선형 증가. 트랙을 들여써도 삐져나옴은 input 자체 가장자리 기준이라 제어 불가(매 수정마다 같은 벽).
     -> 시도했다 실패한 우회: pointer-events:none(트랙)+all(thumb)로 클릭 독점은 풀리나, 투명 native thumb와 별도 시각 div의 위치가 어긋나(native는 inset, div는 순수 %) "핸들 오른쪽만 눌림"이 발생. native thumb을 직접 보이게 해도 증상 2는 그대로.

     -> 원칙: 듀얼 핸들 슬라이더는 native input 2개 겹침으로 만들지 말 것. 브라우저별 thumb inset/이벤트 독점 quirk에 끝없이 부딪힌다. 커스텀 div 핸들 + pointer 이벤트 + inset 보정 % 공식이 유일하게 결정론적이며 브라우저 독립적이다.

D-124. 1회성 "소진 플래그"를 set하는 경로만 있고 reset 경로가 없으면, 관련 리소스를 삭제했을 때 플래그가 남아 기회가 영구 소진되는 패턴 ✅ 해결

D-125. 테이블에 UPDATE RLS 정책·활성화가 없으면 authenticated가 그 테이블의 "아무 컬럼이나" 직접 UPDATE할 수 있어, 결제/권한 컬럼이 클라에서 조작되는 패턴 ✅ 해결
     -> 증상: 기업(authenticated)이 브라우저 콘솔에서 supabase.from('missions').update({trial_unlocked:true}) 또는 {trial_public_panel_ids:[전체]}로 무료 체험을 결제 없이 언락 가능. missions에 UPDATE RLS가 없어(인증된 전체 UPDATE 허용) 모든 컬럼이 무방비.

D-126. 동적 가격에 "시간창(할인 마감·플래시 세일 등)"이 끼면, 클라(표시)와 서버(차감)의 '현재 시각' 기준이 달라 경계 시점에 표시가≠결제가가 생기는 패턴 ✅ 해결(설계 원칙)
     -> 증상 가능성: 무료 체험 첫 언락 30% 할인이 결과 최초 열람(trial_results_seen_at)부터 48h. 클라 배너는 nowTick(브라우저 시계)으로 할인가·카운트다운을 그리고, 서버 unlock RPC는 NOW()(DB 시계)로 할인 적용 여부를 판정. 마감 직전 1~2초에 클라는 할인가를 보여줬는데 서버는 정가를 차감(또는 반대)하면 "본 가격과 빠진 가격이 다르다" 클레임.
     -> 원인: 시간 의존 가격은 D-121의 정적 3요소(엔티티 dedup·결정론적 정렬·동일 공식)만으로 부족하다. '시각'이라는 입력이 두 시스템에서 독립적으로 흐르고, 시계 동기(clock skew)·네트워크 지연으로 경계에서 불일치가 필연적으로 발생한다.
     -> 해결: ① 차감 판정·금액은 서버를 단일 권위로(NOW() 기준), 클라는 '추정 표시'로만 둔다. ② 언락/결제 RPC 반환에 실제 적용가(cost)와 원가(original_cost)·할인여부(discount)를 함께 실어, 화면은 서버 응답으로 사후 정정한다(낙관적 표시 → 응답으로 확정). ③ 마감 앵커(seen_at)는 클라가 못 만지게 보호 컬럼+SECURITY DEFINER RPC로만 세팅(D-125) — 안 그러면 할인창을 무한 연장할 수 있다.
     -> 원칙: 시간창이 가격에 들어가면 "표시는 추정, 결제는 서버 권위 + 응답으로 정정"을 기본형으로 한다. 경계 1초의 표시 불일치를 코드로 완벽히 없애려 하지 말고(시계차로 불가능), 서버가 청구한 실제 금액을 응답으로 돌려주어 사용자가 본 화면을 사후 보정하는 구조로 신뢰를 지킨다.

D-127. "연차→경력 배율·크레딧" 같은 동일 매핑 규칙이 클라이언트 1곳 + 서버 RPC 여러 곳에 중복 정의되어, 한 곳만 고치면 정산이 어긋나는 패턴 ✅ 해결(전수 동시 변경 원칙)
     -> 증상 가능성: 패널 experience(연차) → 보상 배율/언락 크레딧 매핑이 (a)클라 honorLevels.getExperienceMultiplier (b)서버 complete_mission_and_refund (c)서버 recalc_mission_consumed (d)서버 unlock_free_trial_mission 총 4곳에 같은 if/CASE로 복제되어 있다. 연차 구간을 바꿀 때(예: 시니어 8+ → 8~14, 헤드 15+ 신설) 클라만 고치면 패널이 보는 보상(getPanelReward)·기업 언락 표시가는 새 밴드인데 기업 크레딧 실소비(서버 recalc/refund)는 옛 밴드로 계산되어 "본 금액 ≠ 빠진 금액"·"패널 정산액 불일치"가 발생.
     -> 원인: 같은 비즈니스 규칙(밴드 경계·배율)이 언어 경계(JS↔PLpgSQL)를 넘어 물리적으로 4벌 존재. 단일 함수로 공유가 불가능(클라/DB 분리)하므로, 한 곳을 고치고 나머지를 빠뜨리는 누락이 구조적으로 필연. D-121/D-126이 "표시 vs 결제" 2자 정합이라면, 이건 "한 규칙의 N벌 복제" 동기화 문제.
     -> 해결: ① 밴드를 바꿀 땐 4곳(클라 honorLevels + 서버 3 RPC)을 반드시 한 마이그레이션·한 커밋에서 동시 변경하고, 단위값(예: '15년'→3.0/6, '14년'→2.0/4.5, '5년'→1.5/3, '4년'→1.0/1.5)을 클라=서버로 표로 대조 검증한다. ② 숫자 분기는 큰 경계부터(>=15 → >=8 → >=5) 순서로 두어 fall-through 오류를 막는다. ③ experience를 'N년' 숫자 텍스트로 단일화해 키워드('임원' 등) 특수 분기 의존을 줄이고, 키워드 분기는 레거시 안전망으로만 남긴다. ④ getPanelReward·getCareerUnlockCredit·서버 회계 RPC를 같은 입력값으로 런타임 실측해 3-경로(패널 정산·기업 소비·언락) 일치를 확인한 뒤 종료한다.
     -> 원칙: "한 규칙이 코드 여러 벌로 복제되어 있는가?"를 먼저 묻고(grep으로 같은 CASE/정규식 전수), 규칙 변경 시 복제본 전체를 한 번에 고친다. 클라만 고치고 끝내면 돈이 걸린 서버 회계가 조용히 옛 규칙으로 청구된다 — RLS 무음 실패만큼 위험한 "복제 규칙 부분 수정" 함정.

D-129. 플랜 변경 RPC가 잔액을 '절대값 SET'하면 결제한 잔여·구매분이 소멸한다 + "구독분/구매분 구분"을 지갑 분리 없이 단일 잔액+트래커로 구현할 때의 함정 4종 ✅ 해결
     -> 증상: 기업이 Starter→Pro로 바꾸면 grant_plan_credits가 credit_balance를 165로 '덮어써' 스타터 잔여+별도 구매 충전분이 전부 증발(사용자: "둘 다 결제했는데 왜 사라지나"). 근본은 grant_plan_credits/admin_change_plan의 SET credit_balance = v_credits(절대값).
     -> 해결 방향: ① 플랜 결제는 누적(credit_balance += v_credits) ② 월 갱신은 매월 리셋하되 '구매 충전분'은 보존 — 이를 지갑 2개로 쪼개면 소비 RPC(reserve/refund/unlock)·프론트 게이트 전부를 고쳐야 함(블라스트 반경 큼). 대신 단일 credit_balance(소비 단일 진실, 무수정) + addon_credits(보존돼야 할 구매분만 추적하는 트래커)로 구현.
     -> 핵심 불변식: 소비는 항상 "구독분 먼저, 구매분 나중" 규약 → 어느 시점에도 실제 구매분 잔량 = LEAST(addon_credits, credit_balance). 별도 추적 없이 (a)월간_잔여 = GREATEST(0, balance-addon) (b)추가_잔여 = LEAST(addon, balance) 파생으로 구분 표시·확인 모달까지 구현. addon_credits는 stale(실제보다 큼)해도 LEAST가 매 읽기·갱신에서 클램프하므로 표시·회계 항상 정확.
     -> 이 패턴에서 같이 빠지기 쉬운 함정 4종(검수로 발견·교정):
        (1) purchase_credits는 credit_balance += 와 함께 addon_credits += 를 반드시 같이 해야 함(트래커 누적 누락 시 구매분이 월 갱신 때 사라짐).
        (2) ★ admin_change_plan처럼 '절대값 리셋'을 남겨두는 RPC는 addon_credits=0도 함께 set해야 함. 안 하면 balance만 리셋되고 트래커가 남아 다음 월 갱신 LEAST가 '유령 크레딧'을 부활시킴(097).
        (3) ★ 월 갱신 RPC가 FOR 루프 SELECT 스냅샷을 변수에 담아 계산 후 UPDATE하면, 그 사이 동시 충전(purchase_credits) 커밋분을 덮어써 유실(read-then-write race). 해결: UPDATE문 내에서 컬럼을 직접 참조(credit_balance = 플랜크레딧 + LEAST(addon_credits, credit_balance))해 원자화 — READ COMMITTED에서 갱신 직전 최신 행 값을 사용(097).
        (4) 다운그레이드는 클라(버튼 비활성)만으로 부족 — RPC 내부에서도 티어 랭크 비교로 'downgrade_not_allowed' 차단(콘솔 직접 호출 우회 방지).
     -> 원칙: 돈이 걸린 잔액을 '절대값 SET'하는 모든 경로(plan 변경·관리자 강제·갱신)를 grep으로 전수 찾고, 누적이 맞는지/보존 트래커를 함께 갱신하는지/리셋 시 트래커도 0으로 내리는지/동시성에서 컬럼 직접참조로 원자화했는지 4가지를 한 번에 점검할 것. 한 곳만 빠지면 "결제한 크레딧 소멸" 또는 "유령 크레딧 부활"로 회계가 어긋난다.

D-130. localStorage 자동저장 안전망을 도입하면 "정리(remove) 경로"를 모든 무효화 이벤트에서 빠짐없이 호출해야 한다 — 한 경로라도 빠지면 사용자 의사와 모순된 복원 배너가 뜬다 ✅ 해결
     -> 배경: beforeunload 안에서는 DB 비동기 저장(supabase)이 브라우저에 의해 중간에 죽어 보장되지 않음 → 새로고침/크래시 시 작성 중 폼 유실. 표준 해법은 작성 중 폼을 localStorage에 동기 자동저장 후 재진입 시 복원. 단 자동저장은 "쓰기"만큼 "지우기(정리)" 설계가 중요하다.
     -> 증상(검수로 발견): "저장 없이 나가기"(자발적 폐기)가 DB 임시저장만 건너뛸 뿐 localStorage 자동저장본은 안 지워, 사용자가 명시적으로 "저장 안 함"을 골랐는데도 다음 진입 시 "작성 중이던 의뢰가 있습니다" 복원 배너가 다시 떠 본인 선택과 모순.

     -> 원칙: localStorage 같은 클라 안전망을 "쓰는" 코드를 추가하면, 그 데이터를 무효화하는 이벤트 목록(제출·저장·폐기·새로시작·계정전환 등)을 먼저 나열하고 각 경로에 정리 호출이 있는지 1:1 대조할 것. "성공 때 지움"만 구현하고 "사용자가 버릴 때 지움"을 빠뜨리면 안전망이 사용자 의사와 충돌한다. 형제 컴포넌트(4폼 등) 복제 시 grep으로 정리 호출 수가 모두 동일한지 확인.

D-132. Supabase(PostgREST)는 limit 없는 쿼리를 기본 Max Rows 1000행에서 "에러 없이" 절단한다 — 무한 성장 테이블의 limit 없는 쿼리는 규모 도달 시 무음으로 데이터가 증발

D-133. Realtime postgres_changes를 filter 없이 전 테이블 구독하면 "변경 1건 × 동시 접속 구독자 전원" 브로드캐스트로 메시지 할당량·비용이 곱셈 증가한다
     -> 배경: panel/Missions가 missions 전 테이블 UPDATE를 무필터 구독 → 패널 수락 1번(filled_count UPDATE)마다 접속 중인 패널 전원에게 브로드캐스트. 구독자 5000명이면 변경 1건이 메시지 5000건. Sidebar 어드민 뱃지도 panels 전 테이블 구독으로 honor_points 등 무관한 UPDATE마다 재쿼리 유발.

     -> 원칙: supabase.channel().on('postgres_changes', ...) 작성 시 filter 누락을 D-96(채널명 Date.now())과 함께 기본 점검 항목으로 볼 것. 본인 데이터 구독은 user_id/panel_id/company_id eq 필터, 공용 테이블 구독은 관심 상태(eq) 필터가 기본값.

D-134. admin role 게이트를 user_metadata→app_metadata로 전환할 때 `<> 'admin'`/`NOT(...=)` 형태는 app_metadata NULL이 통과해 오히려 새 권한 구멍을 만든다
     -> 증상: 보안 패치(D-58)로 user_metadata→app_metadata 교체 시, 기존 `IF (app_role) <> 'admin' THEN block` 또는 `IF NOT ((app_role)='admin') THEN block` 형태를 그대로 쓰면 일반 사용자(app_metadata.role IS NULL)가 게이트를 통과해버림.
     -> 원인: 일반 사용자의 raw_app_meta_data->>'role'은 NULL(026은 admin 계정에만 app_metadata 세팅). SQL 3치 논리에서 `NULL <> 'admin'` = NULL(거짓 취급) → IF 미발동 → block 건너뜀 → 함수 본문 실행. user_metadata 시절엔 role이 'company'/'panel'(non-null)이라 `<> 'admin'`=true로 우연히 막혔을 뿐, app_metadata로 바꾸면 NULL이라 구멍이 됨.
     -> 해결: 항상 positive 존재 검사 NOT EXISTS로 작성. `IF NOT EXISTS (SELECT 1 FROM auth.users WHERE id=auth.uid() AND raw_app_meta_data->>'role'='admin') THEN block`. NULL이면 EXISTS=false → NOT EXISTS=true → 정상 차단. (IS DISTINCT FROM 'admin' / COALESCE(...,'')<>'admin'도 NULL 안전하나 NOT EXISTS가 가장 명확.)
     -> 적용: 098_fix_admin_rpc_app_metadata_security.sql 7종 전부 NOT EXISTS. + 전환 후 어드민이 app_metadata.role을 실제 보유하는지 확인(미보유 시 어드민 잠김) — 수동 마이그레이션 대비 026 멱등 동기화 UPDATE를 같은 파일 선두에 self-contained 포함.
     -> 원칙: role 게이트의 보안 비교는 NULL 가능 컬럼(app_metadata)에서 부정형(`<>`,`NOT(=)`)을 쓰지 말 것. "관리자가 아니면 차단"은 "관리자임이 증명되지 않으면 차단"으로 뒤집어 NOT EXISTS(=admin)로 구현. D-58과 한 세트로 점검.

D-135. 구버전 함수 본문이 든 stale 마이그레이션 파일을, 그 함수를 나중 번호가 재정의한 뒤에 실행하면 최신 로직이 조용히 되돌아간다 (+ 번호 충돌)

     -> 원칙: 안 돌린 로컬 마이그레이션이 있는 상태에서 원격을 머지하면, 그 파일은 "코드 diff"가 아니라 "DB에 적용될 전체 본문"임을 기억할 것. 같은 함수를 원격이 재정의했는지(git grep "FUNCTION 함수명") 반드시 교차 확인하고, 충돌·회귀 위험이 있으면 변경점만 추출해 최신 번호로 재작성한다.

     -> 원칙: "본인 행의 특정 컬럼만 갱신" 요구가 나오면 self-UPDATE RLS가 아니라 컬럼 한정 DEFINER RPC를 기본 선택지로 둘 것. 그 테이블에 role·status·권한·정산 같은 민감 컬럼이 하나라도 있으면 self-UPDATE RLS는 사실상 금지.

     -> 해결: ① grid-template-columns: repeat(N, minmax(0, 1fr))로 칸이 0까지 수축 허용 ② 고정폭 자식(ScoreBar)에 flexWrap:'wrap'(+ justifyContent center)으로 좁은 칸에서 막대가 다음 줄로 접힘. 둘 다 공용 컴포넌트라 결과 화면(넓으면 한 줄 유지)·공유(좁으면 줄바꿈) 동시 적용.
     -> 원칙: 고정폭 자식을 품는 N등분 그리드는 1fr이 아니라 minmax(0,1fr)을 기본으로 쓸 것 — 1fr 단독은 "컨테이너보다 콘텐츠가 클 때 줄지 못해 터진다". 좁은 컨테이너(사이드바·공유 카드·모바일)에서만 드러나는 잠재 오버플로이므로 넓은 화면 빌드 통과로 안심 금지.

D-151. feedbacks.suggestions(메인 의뢰 이미지 피드백 텍스트)는 두 가지 저장 형식이 공존한다 — 이를 모르고 한 형식만 파싱하면 빈 결과/오분류 ✅ 해결
     -> 상황: 5대 지표 진단 '코멘트 인사이트' 1차 구현이 실제 패널 제출 형식만 파싱 → 시드/예전 의뢰에서 지표별 칭찬/지적이 전혀 안 뜸(빈 화면). 점수(레이더)는 정상이라 "예전 의뢰라 그런가?"로 위장.
     -> 형식 ① 실제 패널 제출(ActiveMission): "[명확성 / 4점] 코멘트" — 지표·점수가 한 줄에 인라인, 어노테이션 1개=1줄.
        형식 ② 시드/레거시: "[명확성]\n코멘트\n코멘트" — 지표 라벨이 단독 줄(헤더), 코멘트는 다음 줄(들), 줄에 점수 없음.
     -> 원인: suggestions의 점수 신호가 형식마다 다른 위치(인라인 vs 없음). 점수 없는 형식은 줄만 봐서는 칭찬/지적을 못 가름.
     -> 해결: 줄을 헤더("[지표...]")/연속줄로 파싱하되, 헤더에 인라인 점수 없으면 feedbacks의 지표 점수 컬럼(clarity_score 등, DIM_LABEL_TO_COL 매핑)으로 폴백해 그 블록 코멘트들의 점수를 정한다. 4~5점=칭찬/1~2점=지적/3점·[총평]·미매칭=제외.
     -> 원칙: feedbacks.suggestions를 파싱하는 코드는 두 형식을 모두 처리할 것. 점수가 줄에 없으면 지표 점수 컬럼 폴백이 유일한 신호다. "한 형식만 가정"하면 데이터 출처(실제 제출 vs 시드/스크립트)에 따라 침묵 실패한다. 점수 컬럼 폴백은 지표 단위라 한 지표에 칭찬·지적이 섞여도 일괄 분류되는 한계가 있으나(형식 ②), 형식 ①(실데이터)은 코멘트별 정확 — 복구 불가한 과거 데이터의 해상도 한계로 수용.

D-152. "특정 미션 타입 전용" 집계 화면은 missions 쿼리에 타입 필터를 명시해야 한다 — is_free_trial 등 다른 exclusion만 챙기다 타입 구분을 빠뜨리기 쉽다 ✅ 해결
     -> 상황: 5대 지표 진단(Diagnosis)·AI 리포트(AIReport)는 메인 의뢰의 5축 점수(clarity/relevance/value/differentiation/trust) 전용인데, missions 쿼리에 type 필터가 없어 서브 의뢰(preference/pricing/email)까지 의뢰 칩·집계에 섞임. 서브 피드백엔 5축 컬럼이 NULL이라 선택 시 데이터 없음/오염.
     -> 원인: 두 쿼리는 원래 type 필터가 없었고, 페이월 작업 때 .neq('is_free_trial',true)만 추가됐을 뿐 타입 구분은 미검토. 규칙13(exclusion 완전성) 목록에 '타입' 항목이 없어 사각지대.
     -> 해결: .or('type.is.null,type.eq.landing_page') 추가(레거시 메인은 type=NULL이라 NULL 포함). Diagnosis 1쿼리 + AIReport 2쿼리.
     -> 수평전개: company/Dashboard는 5축 레이더가 NULL을 v!=null&&v>0로 걸러 점수 오염은 없으나, "승인된 피드백 N건 기준" 카운트(chartFeedbacks.length)에 서브 승인 피드백이 섞여 과대 표기 → chartFeedbacks를 5축 점수 보유 피드백으로 필터해 카운트·게이지·레이더 정합. 단 '총 수집 피드백' Stat(feedbacks.length)은 전 타입 합산이 맞아 유지.
     -> 원칙: 화면이 "메인 전용/서브 전용"이면 missions 쿼리 타입 필터를 exclusion 점검표에 포함할 것. 점수/카운트가 타입별로 NULL이면 집계·카운트 양쪽에서 누락 여부를 따로 확인(레이더는 NULL 무시해도 length 카운트는 안 거른다).

D-155. "Dead RPC/코드"를 제거할 때 그 함수가 어떤 컬럼의 '유일한 갱신원'이고 그 컬럼을 읽는 표시 화면이 남아 있으면, 값이 에러 없이 동결된 채 계속 표시된다(신규=초기값 0 고정 / 기존=구값 stale) ✅ 해결
     -> 상황: update_panel_gamification([신규-J]에서 'Dead RPC'로 호출 제거)가 panels.trust_score·streak_count의 유일한 갱신원이었는데, panel/Dashboard·Profile·admin이 그 컬럼을 계속 표시 → 승인받아도 신뢰도 0% 영구 고정, '이번 주 제출'도 동결. 에러가 없어 수십 회 QA에서도 미발견.
     -> 원인: 제거 시 "이 함수가 쓰던 컬럼을 아직 누가 읽는가"를 grep으로 확인하지 않음. '죽었다'는 판단이 writer(호출 경로) 기준이었고 reader(표시 화면)는 살아 있었음.
     -> 해결: trust_score는 trust_score만 갱신하는 경량 트리거(109, badges/tier 안 덮어씀)로 복구 + 백필. streak_count 표시는 라이브 weeklyCount(feedbacks 7일 비-draft)로 교체. 제거된 RPC가 손대던 컬럼 5종(trust_score·streak_count·tier·last_mission_date·badges) 전수 grep — reader 0인 last_mission_date·tier는 무해로 잔존.
     -> 원칙: RPC/트리거 제거 전, 그 함수가 UPDATE/SET하던 모든 컬럼을 적어 각 컬럼의 reader를 grep으로 전수 확인. reader가 있으면 (a)대체 갱신원 부착 또는 (b)표시를 라이브 계산으로 전환. + 표본 부족 비율 지표(통과율/신뢰도)는 1~2건일 때 0%/100%로 극단 변동·신규 위험 낙인 → N건(예 3) 임계 전엔 '집계 중'으로 표시·판정 보류. 같은 데이터를 두 화면이 다른 분모식으로 산정하면 한 패널에 두 숫자가 떠 꼬임 → 단일 식(decided-only 등)으로 통일(D-35 연계).
