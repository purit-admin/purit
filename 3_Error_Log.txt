## [C] Supabase 연동 규칙
================================================================

C-1. mock data(data.js)와 실 DB 구분
     → src/lib/data.js의 MISSIONS, FEEDBACKS, PANELS 등은 UI 개발/목업용
     → Supabase 연동이 완료된 페이지에서는 data.js 참조 코드 제거할 것
     → 현재 Supabase 연동 완료: companies, panels, missions, feedbacks 테이블

C-2. 트리거 의존 로직 주의
     → 회원가입 시 DB 트리거(handle_new_user)가 자동으로 panels 또는 companies 레코드 생성
     → 프론트엔드 코드에서 signUp 후 수동으로 테이블 INSERT 하지 말 것 (중복 생성 위험)

C-3. 인증 상태는 useAuth() 훅 사용
     → supabase.auth.* 를 직접 호출하지 말고, useAuth 훅의 메서드 사용
     → 예외: AuthContext.jsx 내부 구현

C-4. 피드백 제출 시 3개 테이블 동시 업데이트 패턴 유지
     → feedbacks INSERT → missions.filled_count UPDATE → panels.total_missions UPDATE
     → 순서 변경 금지, 오류 발생 시 전체 롤백 고려
     ※ filled_count / total_missions 증가는 반드시 RPC 사용 (직접 UPDATE 금지)
        - increment_mission_filled_count(mission_id UUID)
        - increment_panel_mission_count(panel_id UUID)
        이유: RLS가 패널의 missions/panels 직접 UPDATE를 에러 없이 무시(0행 업데이트)함

C-5. RLS silent failure 패턴 주의
     → Supabase RLS가 UPDATE를 막을 때 에러를 반환하지 않고 0행 업데이트로 조용히 실패함
     → supabase.from().update() 성공 여부는 error가 아니라 실제 DB 반영 여부로 확인해야 함
     → 크로스 테이블 UPDATE(패널이 missions 업데이트, 기업이 panels 업데이트 등)는
        SECURITY DEFINER RPC 함수를 통해서만 처리할 것
     → 현재 등록된 RLS 정책: panels(SELECT/UPDATE), companies(SELECT/UPDATE),
        missions(SELECT/INSERT/UPDATE), feedbacks(SELECT/INSERT/UPDATE)

## [D] 알려진 이슈 & 주의사항
================================================================

D-1. RLS (Row Level Security) 정책 ✅ 전면 정비 완료
     → panels: SELECT(본인 or admin), UPDATE(본인)
     → companies: SELECT(본인 or admin), UPDATE(본인)
     → missions: SELECT(인증된 전체), INSERT(기업), UPDATE(인증된 전체)
     → feedbacks: SELECT(인증된 전체), INSERT(패널), UPDATE(인증된 전체)
     → 카운터 증가는 SECURITY DEFINER RPC로 처리 (C-4, C-5 참조)

D-3. feedbacks DELETE RLS 없음 — cancel_panel_feedback RPC 필수
     → feedbacks 테이블에 DELETE RLS 정책이 없어 패널이 직접 삭제 불가
     → 수락 취소 시 반드시 cancel_panel_feedback(p_mission_id) RPC 호출할 것
     → RPC는 status='draft'인 본인 피드백만 삭제 (SECURITY DEFINER 내 auth.uid() 체크)

D-5. Recharts RadialBarChart 반원 게이지 구현 시 주의사항
     → startAngle=180, endAngle=0 으로 설정해야 반원
     → background prop을 RadialBar에 직접 넣어야 배경 트랙 표시됨
        (RadialBarChart에 넣으면 무시됨)
     → fill은 data 배열 각 항목에 직접 지정 (RadialBar의 fill prop 무시됨)

D-7. 이미지 업로드 + DB INSERT 타이밍 문제 패턴
     → Storage 업로드 경로에 DB row id가 필요한 경우
     → crypto.randomUUID()로 클라이언트에서 UUID 사전 생성 후
        INSERT 시 id: missionUuid 로 직접 지정해 두 값을 동기화

D-10. 비밀번호 변경 시 현재 비밀번호 재검증 패턴 ✅ 정착
     → supabase.auth.updateUser({ password })만으로는 현재 비밀번호 확인 불가
     → signInWithPassword({ email, password: curPw }) 먼저 호출해 검증
     → 실패 시 "현재 비밀번호가 올바르지 않습니다." 메시지 표시 후 조기 반환
     → 3개 포털 모두 동일 패턴 사용 (company/Account, admin/Account, panel/Profile)

D-17. PurityFilter select 쿼리 중첩 join 패턴
     → missions(title, type, image_urls, description, company_id, companies(user_id)) 중첩 select 가능
     → PostgREST FK 자동 감지: missions.company_id → companies.id
     → 코드에서 fb.missions.companies.user_id 로 접근
     → panels(user_id, name): panels.user_id가 알림 수신자 식별에 사용됨

D-19. ConfirmModal viewport 고정 패턴 ✅ 정착
     → 문제: <main style={{overflow:'auto'}}> 스크롤 컨테이너 내부의 position:fixed 모달이
             뷰포트 기준이 아닌 컨테이너 기준으로 렌더되어 스크롤 시 모달이 사라짐
     → 해결: ReactDOM.createPortal(..., document.body) 로 document.body에 직접 렌더
     → 구현: ConfirmModal 컴포넌트 (src/components/ui/index.jsx) + 커스텀 accept 모달도 portal 사용
     → 주의: portal 내부에서 e.stopPropagation() 필수 (배경 클릭 dismiss 오작동 방지)

D-20. 서브미션 description JSON 하위 호환 파싱 패턴 ✅ 정착
     → 구 포맷: missions.description = raw text (e.g. "가격은 월 9,900원...")
     → 신 포맷: missions.description = JSON.stringify({content, image, productDescription, customQuestions})
     → parseSubDesc(desc, type) 헬퍼 패턴:
        1. JSON.parse 시도
        2. preference: 파싱 결과 전체 반환 (기존도 JSON 포맷이므로 호환)
        3. pricing/email: 파싱 성공 + 'content' 키 있으면 신 포맷으로 처리
        4. 파싱 실패 or 'content' 키 없으면 구 포맷 → {content: desc, productDescription:'', customQuestions:[]}
     → 이 헬퍼는 ActiveMission.jsx, PurityFilter.jsx 양쪽에 동일 구현
     → DB 컬럼 변경 없음 — missions.description TEXT 그대로 사용

D-22. 서브 미션 폼 제출 후 대시보드 redirect 패턴 ✅ 정착
     → 문제: 제출 후 setView('list')로 동일 페이지 목록 뷰로 돌아가 UX가 단절됨
     → 해결: navigate('/company')로 대시보드로 이동
     → 중복 제출 2중 방어:
        1. submittingRef.current (동기 ref) — setSubmitting(true) 비동기 한계 보완
        2. missionUuid unique constraint — DB 레벨 최후 방어
     → React setState는 비동기라 빠른 더블클릭이 submitting state 업데이트 전에 두 번째 클릭을 허용함
        → useRef는 동기적으로 즉시 차단되므로 필수 패턴

D-24. 서브 미션 사이드 테이블 INSERT silent failure 패턴 ✅ 해결
     → 문제: missions INSERT 성공 후 preference_tests/pricing_tests/cold_email_tests INSERT가
             RLS 또는 스키마 제약으로 실패하면 catch로 빠져 navigate('/company')가 실행 안 됨
     → 증상: 미션 제출 버튼 클릭 후 화면이 전환되지 않고 멈춤 (missions는 DB에 저장됨)
     → 해결 1 (등록): 사이드 테이블 INSERT 에러를 `if (tErr) throw tErr` → `if (tErr) console.warn(...)` 으로 변경
             missions INSERT 성공만 보장되면 navigate('/company') 항상 실행
     → 해결 2 (목록): PreferenceTest/PricingTest/ColdEmailTest 목록 뷰를 사이드 테이블이 아닌
             missions 테이블(type 필터)에서 로드 — 사이드 테이블 누락 시에도 목록 정상 표시
             목록 카드 클릭 시 navigate('/company/results?id=…') → Results.jsx가 mission_id로 집계
     → 원칙: missions 테이블이 서브 미션의 유일한 목록 진실 원천 — 사이드 테이블은 응답 집계 보조용
             결과 조회는 response 테이블의 mission_id 컬럼 기준으로 처리 (test_id 의존 금지)

D-25. 패널 대시보드 참여 가능 수 불일치 원인 ✅ 해결
     → 원인 1: Dashboard가 limit(10) 제한으로 최대 10개만 로드 → 실제 수보다 적게 표시
     → 원인 2: 슬롯 꽉 찬 미션(filled_count >= panel_count) 미필터 → Missions.jsx보다 많게 표시
     → 해결: limit 제거 + (m.filled_count || 0) < (m.panel_count || 1) 조건 추가
     → 이후 두 페이지 모두 동일 로직: status='active' + 슬롯여유 + 미참여(feedbackMap에 없음)

D-28. panels 조인 RLS 차단으로 feedbacks 쿼리 전체 실패 패턴 ✅ 해결
     → 증상: Results.jsx에서 피드백이 전혀 표시 안 됨 (대시보드 수치는 정상)
     → 원인: feedbacks 쿼리에서 panels(industry, experience, name) 조인 시
             RLS가 기업 유저의 panels 접근을 차단 → 쿼리 전체 실패 → data=null → feedbacks=[]
     → Dashboard는 panels 조인 없이 feedbacks만 단독 조회하므로 정상 작동
     → 해결: panels 조인 제거
     → 원칙: 기업 유저가 feedbacks를 조회할 때 panels를 직접 join하지 말 것
             (panels SELECT RLS는 본인 or admin 전용)

D-29. 반려 피드백 재제출 시 서브 응답 테이블 중복 INSERT 함정 ✅ 해결
     → 증상: 재제출 시 preference_responses / pricing_responses / email_responses에 INSERT 시도 →
             unique constraint(mission_id + panel_id) 위반으로 에러 발생
     → 원인: 최초 제출 때 이미 해당 테이블에 행이 존재 — 재제출은 신규 행이 아니라 수정임
     → 해결: isResubmit 플래그로 분기 → 재제출 시 INSERT 대신 UPDATE 사용
             (.eq('mission_id', mission.id).eq('panel_id', panel.id) 조건으로 기존 행 UPDATE)
     → 추가 주의: 재제출 시 increment_mission_filled_count / increment_panel_mission_count RPC를
                  절대 호출하지 말 것 — 최초 제출 때 이미 카운트가 증가되어 있음. 재호출 시 중복 집계 발생
     → isResubmit 플래그 판별: URL ?resubmit=<feedbackId> + DB에서 fb.status === 'rejected' 교차 검증

D-30. 이미지 어노테이션 코멘트 debounce 미flush로 제출 시 코멘트 유실 ✅ 해결
     → 증상: 패널이 어노테이션 코멘트를 입력 후 1초 이내에 제출 → 기업 Results에서 "코멘트 없음" 표시
     → 원인: handleUpdateAnnotationComment의 1s debounce 타이머가 handleSubmit 호출보다 늦게 실행됨
             → feedback_annotations.comment가 빈 문자열('')로 남아 기업 화면에서 누락
     → 해결: handleSubmit(이미지 모드) 진입 시 commentUpdateTimers 전체 clear 후,
             annotations 로컬 상태 기준으로 전체 어노테이션 코멘트를 DB에 일괄 동기화 후 submit 진행
     → 적용 위치: ActiveMission.jsx handleSubmit → hasImages 분기 최상단
     → 교훈: debounce로 저장하는 중간 데이터가 있을 때, 최종 제출 시 반드시 pending 타이머를 flush해야 함
             (D-12의 "코멘트 UPDATE debounce 패턴"과 연계 — 저장만 설계해서는 안 되고 flush 로직도 필수)

D-31. template_questions DB 데이터 미존재 시 로컬 폴백 패턴 ✅ 정착
     → 증상: QuestionTemplates.jsx 미리보기 클릭 시 질문 목록이 빈 상태로 표시됨
     → 원인: Supabase question_templates 테이블에 template_questions JOIN 데이터가 없음
             (마이그레이션은 실행됐으나 시드 데이터가 없는 상태)
     → 해결: DB questions 배열이 비어있으면 TEMPLATE_BY_NAME[template.name]?.questions 로컬 폴백
             렌더링 시 DB 포맷(question_text/question_type)과 로컬 포맷(text/type) 모두 지원:
             qText = q.question_text ?? q.text, qType = q.question_type ?? q.type
     → 원칙: Supabase에서 JOIN 데이터를 가져오는 구조 + 동일 데이터가 로컬 상수에도 있을 때
             항상 DB 우선, 로컬 폴백 패턴을 적용해 데이터 누락 시에도 UI가 정상 동작하게 할 것

D-32. missions.description JSON 필드 구조 변경 시 하위 호환 폴백 패턴 ✅ 정착
     → 증상: 기존 저장된 미션(templateQuestions + customQuestions 구조)과 신규 미션(selectedQuestions 구조)이
             동일 파싱 로직을 공유해야 하는데, 단순 교체 시 레거시 데이터가 빈 질문 배열로 표시됨
     → 해결: 읽기 경로(ActiveMission, Results)에서 신규 필드 우선, 없으면 구 포맷 폴백
             const allTypedQs = parsedDesc.selectedQuestions || [...templateQuestions, ...normalizedCustomQs];

D-50. useEffect cleanup을 async 함수 내부에서 return하면 cleanup이 절대 실행되지 않음 ✅ 해결
     → 증상: Supabase Realtime 구독이 컴포넌트 언마운트 후에도 살아있어 메모리 누수 + 경고 발생
     → 원인: async 함수는 항상 Promise를 반환하므로, async 함수 안에서 `return () => cleanup()`을 써도
             useEffect는 cleanup 함수를 받지 못함 (Promise를 받음 — 무효)
             ```js
             useEffect(() => {
               async function load() {
                 // ...
                 const sub = supabase.channel(...).subscribe();
                 return () => supabase.removeChannel(sub); // ← 이 return은 load()의 return (Promise 내부)
               }
               load(); // load()의 반환값(Promise)을 무시 → useEffect cleanup 없음
             }, []);
             ```
     → 해결: let sub = null 을 async 함수 밖(useEffect 콜백 최상단)에 선언,
             async 함수 내부에서 sub에 할당만 하고,
             cleanup return은 useEffect 콜백 최상단에서 직접 반환
             ```js
             useEffect(() => {
               let sub = null;
               async function load() {
                 // ...
                 sub = supabase.channel(...).subscribe();
               }
               load();
               return () => { if (sub) supabase.removeChannel(sub); }; // ← useEffect가 이걸 cleanup으로 받음
             }, []);
             ```
     → 원칙: useEffect 내에서 async 함수를 호출할 때, cleanup(구독 해제·타이머 취소 등)은
             반드시 async 함수 밖 useEffect 콜백 최상단에서 return해야 한다
             async 함수 안의 return은 useEffect cleanup으로 전달되지 않는다

     → 증상: 기업 대시보드가 "불러오는 중..." 상태에서 영원히 멈춤

     → 증상: 20개 태그가 개별 setTimeout으로 각자 사이클을 돌리면 처음엔 엇갈리다가

     → 원칙: 여러 요소가 균등한 시간차로 반복 애니메이션해야 할 때 setTimeout 체인은 절대 사용 금지

     → 원칙: JSX 이벤트 핸들러에서 async 함수를 호출할 때는 반드시 async 콜백 + await 조합을 사용할 것

             → 올바른 패턴: `onConfirm={async () => { await asyncFn(); setModal(null); }}`

D-75. async 함수가 내부에서 try-catch-console.error만 하고 re-throw 하지 않으면 호출자가 항상 성공으로 인식해 데이터 소실을 유발하는 패턴
     → 증상: "임시 저장 후 나가기" 버튼 클릭 시 DB 실패가 발생해도 모달이 닫히고 다음 페이지로 이동.
             사용자는 저장이 된 것으로 착각하지만 데이터는 소실됨 (콘솔에만 에러 출력)
     → 원인: saveDraft() 내부에서 catch(e) { console.error(...) } 로 에러를 삼킴
             → async 함수가 에러를 throw하지 않으면 반환 Promise는 항상 resolved 상태
             → 호출자에서 `await saveDraft()` 는 DB 실패 여부와 관계없이 항상 정상 완료로 인식
             → `await saveDraft(); navigate(dest);` 패턴에서 navigate는 항상 실행됨
     → 해결: 저장 실패를 호출자에게 전파해야 하는 async 함수의 catch에서 반드시 re-throw:
             ```js
             } catch (e) {
               console.error('[SaveDraft] 실패:', e.message);
               setSavingDraft(false);
               throw e;  // ← 호출자에게 에러 전파 필수
             }
             setSavingDraft(false);  // ← finally 대신 try 마지막에 배치 (re-throw 후 finally는 실행되나 throw가 이미 진행됨)
             ```
             호출자에서 try-catch로 잡아 실패 시 이동 차단 + 에러 메시지 표시:
             ```js
             try { await saveDraft(); } catch { setError('저장 실패'); return; }
             navigate(dest);  // ← 성공 시에만 실행
             ```
     → 원칙: "에러를 잡되 UI에는 표시하지 않는다"는 내부 catch 패턴은 일반 fire-and-forget에서만 허용.
             호출자가 성공/실패를 구분해야 하는 중요 작업(데이터 저장, 결제, 상태 변경)은
             반드시 에러를 re-throw해 호출 체인 전체가 실패를 인지할 수 있게 해야 함
             catch 안에 re-throw 없음 = "에러를 삼킴" = 호출자 입장에서 항상 성공

             전혀 다른 위치의 오류처럼 보고할 수 있어 원인 파악이 매우 어려움
     → 해결 1 (즉각): 해당 줄을 재입력하거나 자모 문자만 정확히 삭제
                       VS Code의 경우 Ctrl+G(줄 이동) 후 해당 문자 위치에서 Backspace/Delete
     → 해결 2 (안전망): 동일 함수를 재정의하는 후속 migration을 추가해 DB 적용 상태 보장
                        (migration 049가 migration 046 parse 오류의 안전망으로 047 함수를 재적용한 패턴)
     → 탐지 방법: `grep -P '[\x{3131}-\x{314E}\x{3154}-\x{3163}]' *.sql` 로 자모 문자 전수 검색
                  VS Code: Ctrl+F → 정규식 모드 → `[ㄱ-ㅎㅔ-ㅣ]` 패턴으로 검색
     → 원칙: SQL 파일(특히 SECURITY DEFINER, LANGUAGE, AS $$...$$, RETURNS 등 키워드 근처)을
             한국어 환경에서 편집할 때는 IME가 꺼진 상태인지(영문 입력 모드) 반드시 확인할 것
             git diff로 해당 줄에 비ASCII 문자가 포함되어 있으면 migration push 전 반드시 제거
             migration 실패 후 연쇄 미적용이 의심될 때는 실패 migration 파일의 자모 문자 여부부터 확인할 것

D-85. 전역 cron 함수와 per-user 함수가 동일 행을 동시에 처리할 때 이중 차감 방지 패턴 ✅ 해결
     → 증상: expire_all_panel_drafts(pg_cron)와 expire_panel_drafts(패널 접속 시)가 동시에 실행될 때
             두 함수 모두 동일 만료 draft 행을 처리 → missions.filled_count가 -2 감소 (이중 차감)
     → 원인: 행 선택(SELECT)과 카운터 감소(UPDATE missions)가 두 개의 별도 문장으로 분리되어 있어
             두 트랜잭션이 동일 행을 SELECT한 뒤 각자 UPDATE를 실행할 수 있음
             특히 재작성 draft 만료의 경우: feedbacks UPDATE(→rejected) 후 missions UPDATE(-1)의 2단계 구조
             두 트랜잭션이 feedbacks UPDATE를 동시 시도하면 한 쪽은 0행 업데이트가 되어야 하지만,
             missions UPDATE는 feedbacks UPDATE 결과를 확인하지 않고 진행하면 양쪽 모두 -1이 됨
     → 해결: feedbacks 변경을 먼저 실행 후 GET DIAGNOSTICS v_deleted_row = ROW_COUNT 로 실제 변경 여부 확인
             v_deleted_row > 0 (이 트랜잭션이 경쟁에서 이긴 경우)에만 missions UPDATE 실행
             ```sql
             UPDATE feedbacks SET status = 'rejected' WHERE id = rec.id AND status = 'draft';
             GET DIAGNOSTICS v_deleted_row = ROW_COUNT;
             IF v_deleted_row > 0 THEN
               UPDATE missions SET filled_count = GREATEST(0, filled_count - 1) WHERE id = rec.mission_id;
             END IF;
             ```
             최초 draft 만료(DELETE 패턴)도 동일하게 DELETE 후 ROW_COUNT 확인 → 0이면 missions 건너뜀
     → 적용: expire_all_panel_drafts() (051), expire_panel_drafts() (052) 양쪽 동일 패턴 적용
     → 원칙: "SELECT 후 UPDATE" 패턴에서 두 UPDATE가 서로 다른 테이블을 대상으로 할 때
             첫 번째 UPDATE(feedbacks)의 결과가 0행이면 두 번째 UPDATE(missions)를 건너뛰어야 함
             PostgreSQL GET DIAGNOSTICS ROW_COUNT는 트랜잭션 내 동기적으로 실행되므로 경쟁 조건 없음
             "feedbacks 먼저, missions 나중에" 순서가 역전되면 이중 차감 발생 — 순서 변경 금지

     → 해결 1 (handledRef): `let handled` 대신 `const handledRef = useRef(false)` 를 컴포넌트 레벨에 선언
             useRef는 StrictMode cleanup/remount에서도 초기화되지 않음 (컴포넌트 인스턴스에 귀속)
     → 해결 2 (capturedRoleRef ★ 핵심): capturedPendingRole도 클로저 변수가 아닌 ref로 관리
             `const capturedRoleRef = useRef(undefined)` 컴포넌트 레벨 선언
             - undefined: 아직 초기화 안 됨 / null: 읽었으나 유효한 role 없음 / 'panel'|'company': 정상 값
             useEffect 내부: capturedRoleRef.current === undefined일 때만 localStorage 읽기 + 삭제 실행
               → 1차 실행에서만 localStorage를 읽어 ref에 저장 → 2차 실행에서는 ref 값 그대로 사용
             processSession: `const capturedPendingRole = capturedRoleRef.current;` 으로 ref에서 읽음
     → 해결 3 (?? 'company' 폴백 완전 제거): capturedPendingRole=null이면 에러 표시 + signOut
             `?? 'company'` 는 "정상 흐름을 거치지 않아도 company를 강제 배정"하는 위험한 폴백
             역할 불명 신규 유저에게는 명시적 에러를 보여주고 재시도를 유도할 것
     → 적용 파일: src/pages/OAuthCallback.jsx (migration 059/060과 연계)
     → 구현 코드 (컴포넌트 상단):
             ```jsx
             const handledRef = useRef(false);
             const capturedRoleRef = useRef(undefined);  // undefined=미초기화 / null=읽었으나 없음 / 'panel'|'company'=정상
             useEffect(() => {
               if (capturedRoleRef.current === undefined) {
                 const raw = localStorage.getItem('purit_oauth_role');
                 capturedRoleRef.current = ALLOWED_ROLES.includes(raw) ? raw : null;
                 localStorage.removeItem('purit_oauth_role');
               }
               async function processSession(session) {
                 if (handledRef.current || !session) return;
                 handledRef.current = true;
                 const capturedPendingRole = capturedRoleRef.current;  // ref에서 읽음
                 // ...
               }
             }, []);
             ```
     → 원칙:
             1. useEffect 안에서 "한 번만 실행" 가드(handled 플래그)와 "한 번만 읽는 값"(localStorage) 모두
                반드시 useRef로 컴포넌트 레벨에 선언할 것
             2. let/const 클로저 변수는 StrictMode 이중 실행 시 두 번째 클로저에서 초기값으로 리셋됨
             3. PKCE OAuth 흐름에서 코드 교환은 비동기이므로 SIGNED_IN 이벤트가 2차 useEffect에서 발화할 수 있음
                → "1차에서 handledRef=true → 2차 차단" 전략은 processSession이 1차에서 한 번이라도 호출된 후에만 유효
                → 1차에서 processSession이 미호출된 경우(세션 아직 없음) handledRef=false 그대로 → 2차 차단 안 됨
             4. 프로덕션 빌드는 StrictMode 이중 실행이 없어 재현 불가 → 개발 환경에서만 나타나 발견이 매우 어려움

D-92. SECURITY DEFINER RPC의 신규 레코드 초기값 오류 — 계산 기반 컬럼에 하드코딩 값 삽입 패턴 ✅ 해결
     → 증상: Google OAuth로 가입한 신규 패널의 신뢰도(trust_score)가 어드민 패널 관리에서 100%로 표시됨
     → 원인: create_oauth_user_profile RPC(migration 059/060) 의 panels INSERT에 trust_score = 100 하드코딩

             신규 패널: total_missions=0, 승인 피드백=0 → 수식 기준 0이 정상
             하드코딩 100은 "신뢰도 100%인 검증된 패널"처럼 보여 어드민이 잘못된 판단을 하게 만드는 데이터 오염

             + 이미 잘못 생성된 레코드 보정:
             `UPDATE panels SET trust_score = 0 WHERE total_missions = 0 AND trust_score = 100;`
     → 원칙: SECURITY DEFINER RPC에서 신규 레코드를 INSERT할 때
             "시스템이 사후에 계산·집계하는 컬럼"(trust_score, honor_points, total_missions 등)에는
             절대 0 이외의 하드코딩 값을 넣지 말 것
             INSERT 시점 기준값(미션 0건 = 점수 0)과 DB 계산 공식이 일치해야 시스템 일관성이 유지됨
             확인 방법: RPC INSERT 절의 각 컬럼 값이 "외부 입력값" / "고정 상수(플랜, 상태 등)" / "계산 집계값" 중
             어디에 속하는지 분류 → 계산 집계값은 항상 0/null/기본값으로 초기화해야 함

D-94. 로그인·회원가입 페이지 구분 없이 동일 OAuth 콜백이 신규 계정을 생성하여 로그인 페이지에서 계정이 생성되는 패턴 ✅ 해결
     → 증상 1: 로그인 페이지에서 Google 버튼 클릭 → 미가입 계정으로 인증 → 계정이 DB에 생성됨

     → 원인: OAuthCallback.jsx 코드가 OAuth를 트리거한 출처 페이지(로그인 vs 회원가입)를 전혀 구분하지 않음

             ```js
             // AuthContext.jsx
             async function signInWithGoogle(role, source = 'signup') {
               localStorage.setItem('purit_oauth_role', role);
               localStorage.setItem('purit_oauth_source', source);

             }
             // Login.jsx
             await signInWithGoogle(role, 'login');
             // Signup.jsx
             await signInWithGoogle(role, 'signup');

             if (capturedSourceRef.current === 'login') {

               setError('가입되지 않은 Google 계정입니다. 회원가입 페이지에서 역할을 선택 후 가입해 주세요.');

             }
             ```
             capturedSourceRef: `useRef(undefined)` 컴포넌트 레벨 선언 (capturedRoleRef와 동일 패턴 — D-91)
             미설정 시(localStorage에 source 없음): 'signup' 폴백 — 안전한 기본값
             취소/에러(`?error=`) 경로에서도 `localStorage.removeItem('purit_oauth_source')` 정리 필수
     → 원칙: 동일한 OAuth 콜백 URL을 여러 페이지(로그인·회원가입)가 공유할 때,
             각 페이지의 "의도(로그인 전용 vs 가입 허용)"를 콜백이 구분할 수 있어야 함
             구분 방법: OAuth 트리거 시 localStorage에 source 저장 → 콜백에서 읽어 분기
             capturedRoleRef 패턴(D-91)과 동일하게 useRef를 사용해 StrictMode 이중 실행에서도 값 보존
             모든 localStorage 임시 키(purit_oauth_role, purit_oauth_source)는
             모든 종료 경로(성공·취소·에러·차단)에서 반드시 정리할 것

D-95. 파일 업로드가 포함된 가입 흐름에서 signOut 전에 업로드해야 하는 타이밍 패턴 ✅ 정착

D-96. React StrictMode 이중 실행에서 고정 채널명으로 Supabase Realtime 구독 시 "cannot add postgres_changes callbacks after subscribe()" 에러 패턴 ✅ 해결
     → 증상: 개발 환경 콘솔에 "Error: You can only call .on() before calling .subscribe()" 에러 2건 동시 발생
             (NotificationCenter.jsx:63, company/Dashboard.jsx:409 등 Realtime 구독 위치)
     → 원인: React.StrictMode 개발 환경에서 useEffect가 mount → cleanup → remount 순서로 두 번 실행됨

             ★ 프로덕션(StrictMode 없음): 한 번만 실행되므로 재현 안 됨. 개발 환경 전용 증상
     → 해결: 모든 supabase.channel(name) 호출 시 name에 `-${Date.now()}` 접미사 추가

             src/pages/panel/Missions.jsx: `panel-missions-realtime-${p.id}-${Date.now()}`
     → 원칙: Supabase Realtime supabase.channel(name) 호출 시 고정 문자열을 채널명으로 사용하지 말 것
             `${userId}-${Date.now()}` 조합을 기본 패턴으로 적용 — 사용자별 고유성(userId) + 마운트별 고유성(Date.now()) 동시 보장
             cleanup에서 supabase.removeChannel(subscription)을 올바르게 호출하는 것만으로는 StrictMode 이중 실행을 방어하기에 불충분

D-97. signUp() 후 signOut() 완료 전 navigate() 호출 시 목적지 페이지에서 stale user 세션으로 auto-redirect가 발동하는 Race Condition 패턴 ✅ 해결
     → 증상: 이메일 회원가입 완료 후 로그인 페이지로 이동했을 때 "로그인 처리 중..." 버튼이 순간 깜빡이거나,
             대시보드로 이동했다가 다시 로그인 페이지로 튕겨 돌아오는 현상 발생
     → 원인: Supabase는 signUp() 성공 시 자동으로 세션을 생성함 (사용자가 즉시 로그인됨)
             Signup.jsx 흐름: signUp() → SIGNED_IN 이벤트 비동기 발화 시작 → signOut() → SIGNED_OUT 이벤트 비동기 발화 시작 → navigate('/login')
             navigate('/login')이 실행되는 시점에 onAuthStateChange SIGNED_OUT 이벤트가 아직 처리 중일 수 있어
             AuthContext의 user 값이 여전히 non-null인 채로 Login 컴포넌트가 마운트됨
             Login.jsx useEffect: `if (user && authRole) navigate(DEST[authRole])` → 대시보드로 redirect
             그 직후 SIGNED_OUT 완료 → user = null → 대시보드 RoleRoute가 /login으로 다시 튕김
             이 ping-pong 과정에서 로딩 상태가 순간 노출됨
     → 핵심 오해: await signOut()이 완료되었다고 React state(user)가 동기적으로 null이 되지 않음
             onAuthStateChange는 비동기 이벤트 — setState는 다음 render cycle에서야 적용됨
             navigate() 직후 컴포넌트가 마운트되는 시점의 user 값은 이전 render의 stale 값일 수 있음
     → 해결: Login.jsx auto-redirect useEffect에 successMsg 가드 추가
             ```jsx
             useEffect(() => {
               if (successMsg) return; // 가입 완료 직후는 자동 redirect 안 함
               if (user && authRole) navigate(DEST[authRole] ?? '/company', { replace: true });
             }, [user, authRole]);
             ```
             successMsg는 이메일 가입(location.state?.message)·Google OAuth 가입(?signup=google) 모두 truthy
             → 두 가입 경로 모두 커버 / 일반 로그인(successMsg='') 시 auto-redirect 정상 동작 유지
     → 원칙: "로그인 중인 사용자를 대시보드로 보내는 useEffect"가 있는 페이지로 navigate 직전에
             signOut()을 호출하는 패턴은 항상 이 Race Condition에 취약함
             해결 방향: navigate() 대상 페이지에서 "가입 완료 상태"를 감지해 auto-redirect를 선택적으로 억제할 것
             location.state.message 또는 URL 파라미터(signup=google)를 "auto-redirect 억제 신호"로 활용하는 것이 최소 침습적 해결책

D-98. SECURITY DEFINER RPC의 DECLARE 변수 타입이 실제 DB 컬럼 타입과 불일치하면 SELECT INTO 시 암묵적 캐스팅 실패로 RPC 전체가 NULL 반환하는 패턴 ✅ 해결
     → 증상: `/share/:token` 공유 페이지 전체가 404("공유 링크를 찾을 수 없습니다") 화면 표시
             `supabase.rpc('get_shared_mission', { p_token })` 반환값이 error=null인데도 data=null
             특정 토큰만 실패하는 것이 아니라 모든 share 링크가 동일하게 404
     → 원인: DECLARE 섹션의 변수 타입이 SELECT INTO 대상 컬럼의 실제 타입과 다를 때
             PostgreSQL이 암묵적 캐스팅을 시도하다 실패하면 EXCEPTION을 발생시키지 않고
             SELECT INTO 결과 전체를 NULL로 처리하는 경우가 있음
             구체적 사례: `v_persona JSONB;` 로 선언 후 `missions.persona` (TEXT 컬럼) 값을 SELECT INTO 시도
             → TEXT→JSONB 암묵적 캐스트 실패 (persona 값이 유효한 JSON 형식이 아닌 자유 텍스트이므로)
             → v_id(UUID)를 포함한 SELECT 전체가 NULL로 취급됨 → `IF v_id IS NULL THEN RETURN NULL;` 조건 충족
             → RPC가 NULL 반환 → 클라이언트 `if (!result)` 조건 → setNotFound(true) → 404 화면
     → 진단 어려움:
             1) 클라이언트에서 error 객체가 null이고 data만 null → 일반적인 "토큰 없음" 케이스와 구별 불가
             2) SQL 로그나 Supabase Dashboard의 Functions 탭에도 에러 로그가 남지 않음
             3) SQL Editor에서 `SELECT get_shared_mission('토큰값');` 을 직접 실행해도 NULL 반환만 확인 가능
             → SQL EXCEPTION이 발생하지 않아 PostgreSQL 에러 로그에도 기록 안 됨
     → 해결: DECLARE 섹션의 모든 변수 타입을 DB 컬럼 실제 타입과 정확히 일치시킬 것
             `v_persona JSONB;` → `v_persona TEXT;` (missions.persona는 TEXT 컬럼)
             점검 방법: 정보 스키마 조회로 대상 컬럼의 실제 타입 확인
             `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'missions';`
     → 원칙: SECURITY DEFINER RPC를 작성할 때 DECLARE 섹션 변수 타입은 반드시 DB 스키마의 실제 컬럼 타입을 조회해 맞출 것
             특히 TEXT와 JSONB/UUID/NUMERIC/TIMESTAMPTZ는 서로 암묵적 캐스트가 보장되지 않음
             "타입이 맞겠지"라는 가정은 절대 금지 — 컬럼 타입 확인 없이 DECLARE를 작성하면
             모든 SELECT INTO가 NULL을 반환하는 무음 실패로 이어질 수 있음
             4_DBSchema.txt의 컬럼 타입 정보를 반드시 참조할 것 (CLAUDE.md 조건부 로드 규칙)

D-99. 단일 일상어를 키워드 분류 로직에 사용할 때 동일 단어가 다른 도메인에서 다른 의미로 쓰여 오탐하는 패턴 ✅ 해결
     → 증상: 패널 [수정 필요] 탭·[지급 거절] 탭의 getImprovementTip()에서
             'AI로 작성된 것 같다'는 반려 사유에 t.includes('패턴') 키워드가 포함되어 있었으나,
             패널이 "이용 패턴", "구매 패턴", "행동 패턴" 등 정상 피드백을 작성해도 동일 키워드가 매칭되어
             "실제 경험과 개인 의견을 바탕으로 자신의 언어로 작성해 주세요." 팁이 오표시됨
     → 원인: t.includes('패턴')이 "AI 패턴(AI가 생성한 텍스트 패턴)"과 "이용 패턴/행동 패턴"을 구분하지 못함
             단독 일상어는 출현 빈도가 높고 도메인 의존적이라 키워드 분류기로 사용 시 필연적으로 오탐 발생
             t.includes('생성') 도 마찬가지 — "자동 생성", "콘텐츠 생성" 등 정상 사용 맥락과 구별 불가
     → 해결: 단독 일상어 제거 → AI 관련 복합어 또는 고유명사로 교체
             제거: 'ai', 'chatgpt', 'gpt', 'ai로', 'ai가', 'ai 생성', '복사' 유지, '패턴' 제거, 단독 '생성' 제거
             (ai는 단독 사용 시 영문이므로 한국어 문장에서 오탐 빈도 낮아 유지)
     → 원칙: 한국어 단어는 도메인에 따라 의미가 달라지므로 분류 로직에 단일 단어 키워드를 쓸 때
             해당 단어가 다른 문맥에서도 자연스럽게 쓰이는지 반드시 검토할 것
             대안 1: 복합어 사용 ('ai 생성', 'chatgpt', 'gpt' 등 — 정상 문맥에서 출현 확률 낮음)
             대안 2: 공동 출현 조건 (A AND B 두 단어가 함께 있을 때만 매칭)
             동일 함수가 복수 파일에 복사된 경우 모든 파일을 동시에 수정할 것 (D-35 참조)

D-100. 대시보드 KPI에서 "미처리 = 전체 - 완료" 공식이 중간 상태(반려 등)를 포함해 실제 미처리 수보다 부풀어 있는 패턴
     → 증상: admin/Dashboard.jsx "검토 대기 피드백: N"이 PurityFilter "검토 대기" 탭 실제 건수보다 항상 크게 표시됨
             어드민이 대시보드에서 N건을 보고 PurityFilter 진입 시 실제로는 더 적은 건수만 존재
     → 원인: `pendingFeedbacks = stats.feedbacks - stats.passed`
             stats.feedbacks = submitted(검토중) + rejected(반려됨) + approved(승인됨) — draft 제외 전체
             stats.passed = approved만
             따라서 pendingFeedbacks = submitted + rejected → 반려 피드백이 "검토 대기"에 포함됨
             직관적으로 "미처리 = 전체 - 완료"가 맞아 보이지만, 상태가 3단계(검토중/승인/반려) 이상일 때
             이 공식은 "검토 완료됐지만 실패한" 상태(반려)를 미처리로 오분류함
     → 해결: 별도 submitted count 쿼리 추가
             `.from('feedbacks').select('*', {count:'exact', head:true}).eq('purity_passed', false).eq('status', 'submitted').neq('status', 'draft')`
             또는 stats.feedbacks - stats.passed - rejectedCount 방식으로 반려 건수를 별도 집계 후 차감
     → 원칙: "미처리 = 전체 - 완료" KPI 공식은 상태가 정확히 2단계(처리중/완료)일 때만 유효함
             처리 흐름이 3단계 이상(검토중 → 승인 or 반려)인 시스템에서는
             반드시 목표 상태(검토중=submitted)를 직접 count하거나
             중간 실패 상태(반려=rejected)를 명시적으로 제외해야 함
             D-68(집계 쿼리 draft 필터 누락)과 유사하지만 원인이 다름:
             D-68은 필터 누락, D-100은 공식 설계 오류 — 두 가지 모두 집계 쿼리 작성 시 점검할 것

D-101. 상태 변경(DB 트리거 발화) + 금전 처리가 별개 작업으로 분리되어 있을 때 트리거가 조기 발화하는 비원자성 패턴
     → 증상: 기업이 크레딧 부족으로 의뢰 제출 실패 시, 어드민에게 "새 의뢰 등록" 알림이 먼저 발송된 후
             크레딧 예약 실패로 의뢰가 draft/삭제 상태로 rollback됨
             어드민은 활성화 알림을 받고 PurityFilter 등을 진입하지만 해당 의뢰가 없는 상태
     → 원인: 4개 폼(NewMission·PreferenceTest·PricingTest·ColdEmailTest) 공통 패턴:
             1단계: missions INSERT/UPDATE(status='active') → DB 트리거(on_mission_created / on_mission_activated) 즉시 발화 → 어드민 알림 발송
             2단계: reserve_mission_credits() RPC → 크레딧 부족 시 실패
             3단계: missions rollback(status='draft' 또는 DELETE)
             두 작업이 같은 트랜잭션 안에 없으므로 1단계 완료 시점에 트리거가 발화함
             직관적으로 "INSERT 성공 → 알림 발송"이 자연스러워 보이나 뒤이어 금전 처리가 실패하면 알림이 거짓 알림이 됨
     → 해결 방향 1 (단기): reserve_mission_credits()를 먼저 실행하고 성공 시에만 missions INSERT/UPDATE(status='active') 실행
             크레딧 부족 시 DB 변경 없이 에러 반환 → 트리거 미발화
     → 해결 방향 2 (장기): PostgreSQL 트랜잭션으로 두 작업 묶기 → 크레딧 예약과 미션 상태 변경을 단일 RPC 안에서 처리
     → 원칙: DB INSERT/UPDATE가 트리거(알림·통계 갱신 등)를 발화시키는 시스템에서
             해당 변경 직후 성공을 보장할 수 없는 후속 처리(금전·외부 API·RLS 검증 등)가 있다면
             트리거 발화 시점이 "진짜 성공"인지 반드시 검토할 것
             안전한 순서: [선행 조건 검증(크레딧·권한)] → [주요 상태 변경(INSERT/UPDATE)] → [알림·트리거]
             D-61(AFTER INSERT vs AFTER UPDATE 트리거 커버리지)과 연계 — 트리거가 올바른 시점에 올바른 상태를 발화하는지 함께 점검
