## [B] AI 협업 효율화 규칙
================================================================

B-1. 전체 코드 재출력 금지
     → 파일 전체를 다시 쓰지 말 것
     → 변경이 필요한 부분만 "변경 전 → 변경 후" diff 형식으로 제시
     → 예외: 신규 파일 생성 시에만 전체 출력 허용

B-2. 기존 구현 먼저 확인 후 신규 코드 작성
     → 새 기능 구현 전, 이 문서(1_PRD, 2_Architecture)를 먼저 읽어 기존 구현 확인
     → 유사 기능이 있으면 재사용/확장하고, 중복 구현 금지

B-3. 공용 컴포넌트 재사용 우선
     → 버튼: Btn 컴포넌트 사용 (src/components/ui/index.jsx)
     → 카드: Card 컴포넌트 사용
     → 지표: Stat 컴포넌트 사용
     → 점수 표시: ScoreBar 컴포넌트 사용
     → 태그/뱃지: Badge 컴포넌트 사용
     → 빈 상태: EmptyState 컴포넌트 사용
     → 새 공용 컴포넌트 생성 전 기존 컴포넌트 확장 가능 여부 먼저 검토

B-4. 환경 변수 규칙
     → Vite 프로젝트이므로 클라이언트 노출 변수는 VITE_ 접두사 필수
     → import.meta.env.VITE_* 형식으로 접근
     → process.env.* 사용 금지 (Node.js 방식, Vite에서 동작 안 함)

## [C] Supabase 연동 규칙
================================================================

C-1. mock data(data.js)와 실 DB 구분
     → src/lib/data.js의 MISSIONS, FEEDBACKS, PANELS 등은 UI 개발/목업용
     → Supabase 연동이 완료된 페이지에서는 data.js 참조 코드 제거할 것
     → 현재 Supabase 연동 완료: companies, panels, missions, feedbacks 테이블

C-2. 트리거 의존 로직 주의
     → 회원가입 시 DB 트리거(handle_new_user)가 자동으로 panels 또는 companies 레코드 생성
     → 프론트엔드 코드에서 signUp 후 수동으로 테이블 INSERT 하지 말 것 (중복 생성 위험)

C-3. 인증 상태는 useAuth() 훅 사용
     → supabase.auth.* 를 직접 호출하지 말고, useAuth 훅의 메서드 사용
     → 예외: AuthContext.jsx 내부 구현

C-4. 피드백 제출 시 3개 테이블 동시 업데이트 패턴 유지
     → feedbacks INSERT → missions.filled_count UPDATE → panels.total_missions UPDATE
     → 순서 변경 금지, 오류 발생 시 전체 롤백 고려

## [D] 알려진 이슈 & 주의사항
================================================================

D-1. RLS (Row Level Security) 정책
     → 현재 프론트엔드 코드에 RLS 관련 명시적 처리 없음
     → Supabase 대시보드에서 정책 확인 필요
     → company는 자신의 missions/feedbacks만, panel은 자신의 feedbacks만 조회 가능해야 함

D-2. Admin 포털 DB 연동
     → Admin 포털 (PanelManagement, Revenue 등)은 현재 Supabase 연동 일부 미완성
     → 실제 데이터가 아닌 목업 데이터로 표시될 수 있음

D-3. 알림(NotificationCenter) 데이터
     → 현재 알림은 하드코딩된 NOTIFS_BY_ROLE 데이터 사용
     → 실 알림 시스템(notifications 테이블) 미구현 상태
