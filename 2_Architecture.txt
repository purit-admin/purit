## Supabase 쿼리 최적화 원칙 (확장성 대응, 2026-06-05 적용)
================================================================

  ### 전체 테이블 무제한 로드 금지 원칙
  아래 쿼리는 기업/패널 수가 늘어나면 응답 크기 폭발 → 반드시 limit 또는 필터 적용:
  ※ Supabase(PostgREST)는 limit 없는 쿼리를 기본 Max Rows 1000행에서 "에러 없이" 절단함 (D-132) —
    무한 성장 테이블(panels·missions·feedbacks·invoices)의 limit 없는 쿼리는 규모 도달 시 무음으로 데이터가 증발.
    잔여 스케일 항목·수정 트리거 규모는 agent/QA_니체_PROGRESS.txt 🔵 스케일 섹션 참조 (스케일-A/B/E/F/G/H).
  - feedbacks 전체: limit(300~500) 또는 탭별 status 필터 (PurityFilter, Revenue)
  - notifications 전체: limit(200) (NotificationCenter)
  - panels 전체: 명시적 컬럼 select (select('*') 금지) (PanelManagement)
  - missions(패널 뷰, Missions.jsx): .eq('status','active') 기본 + 본인 진행중(draft/rejected) 미션 id만 .or()로 추가 조회 ★ 2026-06-13
    (이어하기·수정 필요 탭이 종료 미션도 표시해야 하므로 단순 active 단독 필터는 회귀 — 5_CodeMap 참조)

  ### Realtime 구독 필터 원칙 (D-133) ★ 2026-06-13
  postgres_changes 구독은 반드시 filter를 지정할 것 — 무필터 전 테이블 구독은
  "테이블 변경 1건 × 동시 접속 구독자 전원" 브로드캐스트로 Realtime 메시지 할당량·비용이 곱셈 증가.
  - panel/Missions: missions 구독 filter:'status=eq.active'
  - Sidebar(어드민 심사대기): panels 구독 filter:'status=eq.pending'
  - 나머지 채널(NotificationCenter·company/Dashboard·Sidebar 알림/반려 뱃지): user_id/company_id/panel_id 필터 기적용

  ★ Realtime 발행(publication) 등록 필수 — 운영 사실 (2026-06-18, D-158)
    postgres_changes 구독은 코드/빌드가 정상이어도 해당 테이블이 supabase_realtime publication에 없으면
    "에러 없이 무음으로" 이벤트가 안 옴(구독은 성공·콜백만 영영 미발화). 운영 DB는 아래 4테이블이 발행에 등록돼야 실시간 동작:
      notifications(알림 뱃지) · missions(새 미션·대시보드) · panels(어드민 심사대기 뱃지) · feedbacks(패널 '수정 필요' 뱃지)
    초기 운영 DB에 발행이 비어 있던 것을 발견(니체 전수조사) → ALTER PUBLICATION supabase_realtime ADD TABLE <t> 로 4종 등록.
    ※ DB 리셋/마이그레이션 환경 재구성 시 재등록 필요. 위 구독은 전부 필터(user_id/company_id/panel_id/status) 보유라 발행 켜도 D-133 안전.
    ※ pg_cron 'lift-panel-suspensions'(매시간 0 * * * *, lift_expired_panel_suspensions — 임시정지 자동 해제) 등록도 같은 전수조사에서 확인·등록(078 수동 스케줄).

  ### 중첩 JOIN 축소 원칙
  missions → feedbacks → panels 3중 중첩은 응답이 기하급수적으로 커짐:
  - Admin/Missions.jsx: 초기 로드 `feedbacks(id, status, purity_passed, submission_deadline, rejection_deadline)` (panels 중첩 제거)
    선택 미션 피드백 상세(MissionDetail): 별도 select + panels(name) lazy load
  - Panel/Dashboard.jsx: `missions.select('...')` 에서 `feedbacks(id)` 중첩 JOIN 제거
    슬롯 체크는 `filled_count`, `panel_count` 컬럼 직접 사용

  ### 벤치마크 데이터 전체 로드 금지
  - company/Diagnosis.jsx: 전체 회사 승인 피드백 로드 대신 DIMENSIONS 배열의 정적 `d.benchmark` 상수 사용
    (전체 로드 시 크로스컴퍼니 데이터 접근 + DB 부하 동시 발생)

  ### 매 대시보드 진입 알림 쿼리 최적화
  - panel/Dashboard.jsx 마감 임박 알림: 쿼리 3개(별도 feedbacks 조건) → 1개(draft+rejected 통합) + 1개(notifications 중복 체크)

  ### 일괄 처리 배치 쿼리 원칙
  - PurityFilter bulkApprove/bulkReject: rejection_deadline UPDATE는 메인(4h)/서브(2h) 2개 배치 UPDATE
    알림 발송: forEach sendNotification (N쿼리) → 배열 INSERT 1회

  모든 페이지네이션 컴포넌트는 전체 번호 렌더(Array.from{length:totalPages}) 금지 → WINDOW=5 슬라이딩 윈도우:
  - 적용 완료: company/Dashboard, panel/Missions, panel/History, company/Results, NotificationCenter
  - 패턴: winStart=max(1, page-2), winEnd=min(totalPages, winStart+4) → pageNums 슬라이스
